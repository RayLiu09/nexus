# NEXUS 数据资产平台软件参数文档

**版本**：V1.0  
**适用范围**：NEXUS P0 单节点部署、试点环境建设及软件验收  
**产品形态**：企业级 Web 数据与知识资产管理平台

## 一、软件整体要求

### 1.1 总体架构要求

NEXUS 应采用前后端分离、服务化和适配器解耦的架构，形成“数据接入 → 接入校验 → 资产化 → 解析/标准化 → AI 治理 → 规则护栏 → 知识切片/索引 → 权限过滤检索”的完整链路。文档处理 Pipeline 和结构化记录处理 Pipeline 必须在作业创建时明确路由，Worker 不得根据运行时数据临时推断处理类型。

平台应区分 `assetize` 与 `normalize` 两个阶段：前者创建资产和版本锚点，后者生成统一的 `normalized_document` 或 `normalized_record`。治理输入只能是 `normalized_asset_ref`，不得直接使用原始文件、原始 JSON 或 MinerU 原始输出；治理结果和知识切片均应能够回溯到标准化引用、版本和原始对象。

### 1.2 软件与中间件基线

| 软件层 | 要求 |
| --- | --- |
| 后端控制面 | Python 3.11、FastAPI 0.115+、Pydantic v2、SQLAlchemy 2.x、Alembic |
| 依赖管理 | 使用 `pyproject.toml` 和 `uv.lock`，通过 uv 管理 Python 依赖 |
| 前端控制台 | React 19、Next.js 16 App Router、TypeScript |
| 数据库 | PostgreSQL 15+，启用 pgvector 扩展 |
| 对象存储 | MinIO，保存原始对象、解析工件、图片和标准化文件 |
| 异步作业 | PostgreSQL Job 表 + 后台 Worker 轮询；支持行级领取、锁租约、心跳、重试、退避和死信状态 |
| 文档解析 | MinerU，按 MIME 类型自动选择 `pipeline`、`vlm` 或 `MinerU-HTML`；图片、PDF、TIFF 自动启用 OCR |
| AI 网关 | 使用既有 LiteLLM，负责模型路由、供应商适配、凭据和网关侧限制；NEXUS 不建设独立 AI 网关 |
| 检索服务 | 通过检索适配器接入；P0 默认采用 PostgreSQL pgvector，向量后端可按规模扩展替换 |
| 向量模型 | `bge-large-zh-v1.5`，重排模型使用 `bge-reranker-large` |
| 缓存 | P0 使用进程内 TTL 缓存；Redis 为后续扩展组件，不作为 P0 必选依赖 |

### 1.3 数据、安全与审计要求

平台应使用本地 `identity-org-service` 管理用户、角色、API Caller、API Key 和组织范围，钉钉组织同步为可选适配。访问控制采用 RBAC、组织范围和数据分级联合过滤，权限过滤必须发生在检索和 API 返回前。

导入数据默认按 L1/L2 处理。L3/L4 仅在存在明确高敏感证据、审批和规则依据时启用复核、脱敏和授权控制。未经批准的 L3/L4 明文不得发送给外部模型。日志不得记录 API Key、敏感明文或大段原始内容。

Prompt、规则、治理结果、版本状态、权限、API Key、AI 采纳和人工覆盖等变更必须记录审计事件。接入批次、原始对象持久化、接入校验完成、版本状态变化和 Pipeline 失败应具备标准事件和 `trace_id`。

### 1.4 性能与质量指标

在基准部署和正常负载下，资产列表接口 P95 应小于 200 ms，资产详情接口 P95 应小于 150 ms，检索接口 P95 应小于 1 s，问答接口 P95 应小于 5 s。小批量数据从接入到可检索目标小于 15 分钟，单资产 AI 治理 P95 小于 30 秒（不含解析和索引）。

平台应达到标准化资产、治理决策、AI 运行、质量评分和关键操作审计 100% 可追溯；权限泄露率为 0；MinerU 解析成功率不低于 95%；问答结果引用覆盖率为 100%。

## 二、功能模块要求

功能模块以 `nexus-console` 实际导航为准，导航分为总览、数据工程、资产与治理、访问与审计、个人工作五组。

### 2.1 总览

**工作台**：展示接入批次、原始对象、标准化、AI 治理、待复核、作业和基础运行状态等概览，支持从异常或待办直接跳转到对应模块。

### 2.2 数据工程

**数据源**：支持本地文件、NAS、Crawler、数据库和 API 推送等数据源登记，维护来源信息和默认治理提示。  
**原始数据台账**：查看接入批次、原始对象、校验摘要、校验和及追溯/回放入口。  
**作业中心**：展示作业阶段、关联对象、失败原因和重试次数，支持重试、重处理、重治理和失败定位。

### 2.3 资产与治理

**资产目录**：提供资产列表、当前版本读模型、版本历史、标准化引用、标签、组织范围和索引状态查询。  
**治理审核**：对 `review_required` 资产提交最终分类、分级、标签、质量处置、组织范围和复核原因。  
**治理追踪**：查看 AI 治理运行、建议、置信度、质量评分、规则命中、决策轨迹和正式治理结果。  
**规则配置**：维护分类、分级、标签、质量评分和知识类型规则；保存后对后续治理运行生效，并进行 Schema 校验、ETag 并发控制和审计。  
**治理 Prompt**：维护治理流水线各任务类型的 Prompt 模板，编辑生成新版本并归档旧版本。  
**AI Prompt**：维护 AI 治理和质量评分 Prompt 配置、LiteLLM 别名引用、输出 Schema 版本等，不提供模型密钥和网关路由管理。

### 2.4 访问与审计

**权限与审计**：维护本地用户、角色、组织范围、API Key、审批和审计日志。  
**API Caller**：维护上层系统调用主体、凭据、接口权限和启停状态。  
**智能检索**：提供权限范围内的资产检索和问答，结果必须返回来源资产、版本、标准化引用和知识切片定位。  
**检索联调**：用于管理员和业务专家验证召回、过滤、重排、引用和调用方权限模拟，不改变正式治理结果。

### 2.5 个人工作

**我的工作区**：汇总当前用户的待办、复核任务、近期处理记录和个人关注内容。

## 三、硬件配置要求

### 3.1 P0 单节点推荐配置

| 设备项 | 推荐配置 | 用途说明 |
| --- | --- | --- |
| CPU | 16 核，主频不低于 2.4 GHz | API、Worker、标准化和索引任务的并行处理 |
| 内存 | 64 GB 及以上 | PostgreSQL、应用服务、Worker 和解析任务运行 |
| GPU | 显存 48 GB 及以上 | MinerU `vlm`/HTML 解析及需要 GPU 的文档任务；无复杂任务时可降配但会降低吞吐 |
| 系统盘 | SSD 480 GB 及以上 | 操作系统、容器、日志和运行时文件 |
| 数据盘 | 企业级 SSD 2 TB 及以上，可扩展 | PostgreSQL 数据、MinIO 对象、解析结果、图片和索引投影 |
| 网络 | 千兆以太网，建议万兆上联 | 文件上传、对象存储、模型服务和上层 API 访问 |
| 操作系统 | 64 位 Linux，建议 Ubuntu Server 22.04 LTS 或同等级发行版 | 运行数据库、容器、Worker 和 MinerU |

### 3.2 单节点并发建议

推荐同时运行 8-12 个 Pipeline 作业，P0 上限为 16 个；MinerU 文档解析建议并发 2-4 个、上限 4 个；结构化标准化建议并发 4-8 个；AI 治理/质量任务建议并发 2-4 个、上限 6 个；索引同步建议并发 2-4 个、上限 6 个。实际值应根据文档复杂度、模型响应时间和磁盘吞吐调整。

### 3.3 部署与扩展要求

PostgreSQL、MinIO、NEXUS API、Console、Worker、MinerU Router 和 LiteLLM 应支持容器化部署，并配置独立的数据卷、备份策略和日志保留策略。GPU Worker 应与 CPU Worker 隔离，避免解析任务争抢 API 和数据库资源。

当活跃作业持续超过 16 个、队列等待 P95 连续三天超过 5 分钟，或 MinerU 解析队列 P95 连续三天超过 20 分钟时，应评估横向扩容。扩展阶段可引入 RabbitMQ/Celery、Redis、独立向量检索引擎和 MinerU 多节点集群，但这些组件不属于 P0 单节点必选配置。
