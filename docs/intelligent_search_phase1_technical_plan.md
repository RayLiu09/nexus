# 智能检索第一阶段：技术路径与组件选型

日期：2026-11-04
状态：第一阶段实现与针对性验证完成（2026-11-05）；人工 Review Gate 待合并前完成。

## 1. 目标与范围

将“智能检索”升级为模型选择业务函数、服务端执行查询、依据证据生成回答的 Chatbot。第一阶段覆盖公开业务查询、聚合、证据补全，以及无结果或证据相关度不足时的联网补充；回答展示引用出处，界面实时展示执行动作。

工具契约以 [public-function-tools](generated/public-function-tools/README.md) 和 [公开消费合同](api/public_agent_data_api.md) 为依据。现有目录包含 55 个工具，接入时按用途筛选：业务查询、聚合和证据读取完整覆盖；排除递归调用检索路由、嵌套问答及原始文件下载链接等不适合模型执行的工具。

本阶段提供有预算限制的执行流程，为后续多轮、多步骤编排保留接口；会话持久化、自主循环规划和通用写入型工具留到后续阶段。联网结果可由部署开关选择是否进入现有资产处理流程。

## 2. 组件选型

| 层次 | 选型 | 用途及理由 |
| --- | --- | --- |
| Chatbot 界面 | React 19 + Next.js 16，`@ant-design/x` 2.10.0 | 已验证 React 19 / Ant Design 6 的 peer 兼容性，使用 Bubble、Sender、ThoughtChain 展示消息、输入和执行动作。 |
| 回答与图表 | 复用 `react-markdown`、`remark-gfm`、ECharts | 流式 Markdown、列表、表格和已有图表展示；引用使用独立结构化数据渲染，限制不安全链接和 HTML。 |
| 实时通信与状态 | 复用 Fetch + SSE，自定义 React Hook / reducer | 单向事件流已能支持动作进度与回答增量；统一维护当前轮次、动作、引用和终止状态，支持停止生成。 |
| API 与执行层 | `nexus-api` FastAPI + 受控 HTTP 执行器，复用 `nexus-app` 能力 | 保留现有查询入口，通过固定配置的公开 API origin 调用业务接口，集中处理身份、参数校验、超时及审计。 |
| 工具定义 | 生成的 Chat Completions tools + HTTP bindings | 使用稳定函数名与 OpenAPI 参数契约；按业务类别加载工具，避免每次发送全部工具。执行器按 HTTP bindings 调用已有公开接口，服务端从 `BUILDIN_API_CALLER` 注入凭证。 |
| 模型与 Prompt | 现有 LiteLLM + `ai_prompt_profile` | 模型负责工具选择、参数生成和证据回答；沿用模型路由、凭证管理与 Prompt 版本管理。 |
| 参数与结果校验 | Pydantic v2 + OpenAPI / JSON Schema 校验 | 校验完整参数结构、枚举、范围和额外字段；工具结果归一化并限制大小，不能仅依赖模型输出合法 JSON。 |
| 本地语义检索 | 现有 pgvector 检索适配器与 embedding 配置 | 保留现有索引、显式检索范围和过滤语义；先改善数据覆盖与证据完整性，通过评测再决定重排优化。 |
| 联网搜索 | 优先 `search_web_search`（DeepSeek Search），按配置支持 `search_firecrawl` | 复用已有公开搜索能力，保留网页标题、URL 和来源信息；执行器以 `INGEST_SEARCH_RESULTS` 覆盖 `auto_ingest`，默认 false。 |
| 验证 | pytest、Vitest / Testing Library、Playwright | 覆盖工具契约、访问控制、联网触发、引用准确性、SSE 生命周期与 Chatbot 交互。 |

## 3. 实现技术路径

```text
用户提问
  → 携带真实登录身份创建本轮执行上下文
  → 发现资源 / 识别业务类别，加载相关工具
  → 模型选择查询或聚合函数并生成参数
  → 服务端校验、鉴权、执行，实时推送动作事件
  → 按结果补全文档章节、切片、图谱或业务记录证据
  → 判断证据是否足够；必要时联网补充
  → 汇总可追溯来源，流式生成带引用的回答
```

1. **接入工具注册与可信执行层。** 覆盖文档、教材、教学标准、课程、培养方案、职业能力、市场岗位、专业布点、企业、园区等公开业务资源，以及现有聚合和证据工具。按用户决策，执行器通过 HTTP 调用现有公开 API，服务端使用 `BUILDIN_API_CALLER` 作为 API 调用凭证，沿用调用者有效性及权限检查。Console 登录鉴权、查询发起人的审计归属分别保留；API 调用身份不等于用户身份。凭证不进入模型参数、浏览器或日志。只读 POST 按业务语义准入。
2. **形成有界的模型函数调用流程。** 采用“资源发现 / 实体解析 → 主查询或聚合 → 证据补全 → 回答”的有限阶段；必要步骤可消费上一步返回的实体或引用 ID。设置工具次数、输入输出、执行时长预算；第一阶段不开放无限自主循环。模型不能自行构造 SQL、HTTP 地址或越过工具白名单。
3. **保留业务查询和统计口径。** 市场岗位使用当前 `query_market_jobs` / `aggregate_market_jobs`；专业布点使用 `list_major_offerings` / `aggregate_major_offerings`。统计使用全量筛选集上的聚合接口，展示筛选条件、分组、数据覆盖与时间口径；不从分页样本推算总体，不生成接口未支持的统计结论。
4. **补全证据并判断联网条件。** 根据返回的真实 ID 读取章节、切片、目录节点上下文或证据包。无命中、语义召回最高分低于初始阈值 0.65，或模型判断证据不足时，允许联网补充；阈值仍需业务样本校准，不将不同工具分数当作统一置信度。聚合结果不使用网页替代统计口径。用户明确限定本地数据或指定资产时保持该范围；接口异常与无数据分别处理。仅将通过敏感信息检查的用户原始问题用于搜索，不发送本地证据正文。
5. **建立统一引用数据。** 服务端根据实际工具返回构建来源注册表，模型仅引用注册表中的编号。生成后校验引用编号，缺少证据的判断明确标记。内部文档、结构化记录、统计结果和网页分别展示合适的出处字段；不为独立业务记录伪造文档引用。
6. **重构 Chatbot 页面。** 保留“智能检索”入口，采用消息流、底部输入区、停止按钮、推荐问题、可折叠动作过程和来源卡片。回答中的 `[1]` 等编号可打开出处详情；网页来源链接跳转原网页，内部引用定位到有权限的资产或证据详情。显示部分成功、无结果、失败、取消等状态。

## 4. 为下一阶段保留的契约

| 契约 | 第一阶段实现内容 |
| --- | --- |
| 执行上下文 | `request_id`、`turn_id`、真实 actor、访问范围、取消信号、执行预算；会话 ID 作为后续扩展字段。 |
| 动作事件 | `event_id`、递增 `sequence`、`turn_id`、`action_id`、可选 `parent_action_id`、动作类型、工具名、状态、起止时间、脱敏摘要；状态包含 running / completed / failed / cancelled。 |
| SSE 事件 | 保持现有 meta / step / chunk / final / error / done 兼容，扩展动态动作与引用数据；final 汇总结果，done 结束本轮。实时过程展示执行事实与结果摘要。 |
| 来源数据 | `citation_id`、来源类型、标题、证据摘要；文档附资产 / 版本 / normalized ref / chunk / 章节定位，业务记录附真实记录 ID，聚合附工具及筛选口径，网页附 URL、可用的发布信息和访问时间。 |
| 工具结果 | 统一 success / empty / error，保留原始业务语义、截断及续读信息；Session 不跨线程共享。后续编排可复用同一执行器和事件协议。 |

## 5. 实施顺序与验收

按三个可独立验证的小包推进：**工具执行与访问边界 → 证据引用与联网补充 → Chatbot 界面及端到端验证**。开始业务代码前创建对应任务包并冻结接口；实现时同步更新架构、需求与页面原型文档。

- 工具接入：生成目录漂移检查通过；业务查询、聚合、证据读取均有契约与代表场景测试。
- 访问边界：保持 available / current-ref、正式分类及既有敏感数据策略；明确当前 `open:*` 尚无组织过滤，Console 适配必须验证用户授权，不能据此宣称已实现组织隔离。
- 联网与引用：覆盖无结果、低相关度、显式限定范围、搜索失败；验证开关默认关闭且模型不能覆盖，开启后仅合格结果进入现有处理流程，引用有真实出处、内外来源可区分。
- 实时交互：动作开始 / 完成 / 失败及时可见；停止后当前轮次进入终止状态；历史轮次与当前执行互不混淆，移动端可使用。
- 检索质量：用同一批业务问答对比重构前后工具选择、证据命中、引用正确性、回答支撑度和延迟。预期收益来自完整业务覆盖、真实聚合与证据补全；提升幅度以评测结果为准。

第一阶段已落地 52 个公开工具（55 个生成工具中排除 3 个），按主查询和证据阶段提供给模型；搜索由执行策略触发。预算为最多 16 次 HTTP 工具调用、180 秒调度期限，每次 HTTP 调用超时 25 秒，模型客户端超时上限 45 秒且不进行 SDK 自动重试。正在执行中的同步调用仍受其自身超时约束，180 秒不代表严格的整轮墙钟上限。完成后按 `WORKFLOWS.md` 提交 API、AI 治理、语义检索、权限 / 审计和前端 UX 的 Review Gate 证据；真实质量提升比例需要另做同题对照评测。

## 6. 实施前澄清

### 实时过程与 API 工作量

复用链路为浏览器 Fetch → Next.js `POST /api/query/stream` → FastAPI `POST /internal/v1/query/stream`，并已支持 meta / step / chunk / final / error / done 事件。因此本阶段新增 HTTP 路由为 **0**，主要扩展动态工具动作、执行编号、来源数据和终止状态，以及完善代理断开传播与服务端取消检查。

仅“实时过程通道改造”初步估算为 **1–2 人日**：后端事件与终止处理约 0.5–1 人日，前端事件状态、过程展示联调和测试约 0.5–1 人日；不包含完整工具接入、Chatbot 整体视觉重构与检索质量评测。停止后不再启动后续动作；已经提交给外部供应商的同步调用能否立即中断，取决于客户端与供应商支持，必须用超时约束其占用。

### Prompt 新增与持久化

已新增两个受管理的业务 Prompt：`retrieval.public_tools_v1`（选择工具、生成参数、按有界阶段使用工具结果）与 `retrieval.evidence_answer_v1`（根据证据和引用注册表生成回答）。沿用现有查询扩展 Prompt；为兼容原检索链路，保留已有意图、参数提取和答案组织配置。

默认模板及幂等初始化代码位于 `nexus-app/nexus_app/retrieval/prompt_profiles_public_tools.py`，随 Git 版本管理；初始化后正式持久化到 PostgreSQL 的 `ai_prompt_profile.prompt_template`。运行时只读取该表的 active 配置，继续使用 `PromptProfileService` 的版本与审计机制，并接入现有 Prompt 管理场景及允许变量校验。初始化不覆盖用户已有配置。

工具参数 Schema 与 HTTP 映射仍来自 `docs/generated/public-function-tools/`；它们属于接口契约，与业务 Prompt 模板分别管理。工具白名单、鉴权、只读限制和预算由服务端执行，不依赖提示词约束。

### 受控执行适配层与接口数量

适配层是后端内部代码模块，不是新 HTTP 服务，也不为每个函数新增一套 API。已复用现有 `/query`、`/query/stream` 入口，通过环境配置的 API Key 调用已有 `/open/v1` 公开接口，对工具名称、参数、API 调用者、查询发起人、结果和引用进行映射；公开路径保持原有业务契约。

主要工作在“每类工具的访问策略与返回结构适配”，而非创建路由：共享参数校验、预算和审计基础设施，按资源类型补充适配及测试。公开调用者和 Console 用户的身份语义必须分别处理，现有 `open:*` 不具备组织过滤，不能直接视作 Console 用户授权检查已完成。

### 用户确认的环境配置

服务端当前默认读取仓库根目录 `.env.dev`，该文件受 Git 忽略。已在本地设置用户提供的初始凭证，本文不记录凭证值。环境变量约定如下：

```dotenv
# 服务端公开业务 API 凭证；部署时填写，不提交实际值。
BUILDIN_API_BASE_URL=http://127.0.0.1:8000
BUILDIN_API_CALLER=
INGEST_SEARCH_RESULTS=false
```

- `BUILDIN_API_BASE_URL` 指定公开业务 API 的固定 origin，默认 `http://127.0.0.1:8000`；容器部署填写可达服务地址。只允许 HTTP(S) origin，不携带路径、凭证或查询参数，修改后重启 API。
- `BUILDIN_API_CALLER` 名称按用户指定拼写保留；Settings 使用 SecretStr 遮蔽，执行器发送请求时才读取实际值。
- `INGEST_SEARCH_RESULTS=false`：智能检索调用搜索接口时显式传入 `auto_ingest=false`，仅返回带来源的搜索结果。
- `INGEST_SEARCH_RESULTS=true`：传入 `auto_ingest=true`，复用现有搜索入库的去重、内容质量与来源准入，随后进入现有资产处理流程；不直接生成 available 资产。当前轮次仍将这些结果标记为外部来源。
- 该开关控制智能检索执行器，模型传入的 `auto_ingest` 必须被服务端配置覆盖；独立公开 API 调用者沿用已有接口约定。
- 已完成配置字段、本地环境文件、HTTP 执行器注入、入库参数覆盖与真实用户审计接线；Console 内部查询已使用新链路，外部查询兼容入口保留原路由。

## 7. 最终交互与验证记录

- 对话和输入框铺满页面可用宽度，不受固定居中最大宽度限制；支持窄屏。
- 引用来源默认收起；行内引用可直接打开详情。来源只展示业务标题、正文或可读摘要、中文查询条件及原文入口，不展示 UUID、内部 key 或原始 JSON。定位锚点保留于结构化数据中。

## 2026-11-05 引用、预览及显式联网补充

以本节取代前述自动联网兜底的第一阶段交互：输入框底部“联网搜索”默认关闭，内部请求增加严格布尔
`web_search=false`。开启后不依赖本地是否命中，调用现有 `search_web_search`（DeepSeek，`count=10`）；
提供方实际返回不足 10 条时如实展示。保留敏感问题/明确本地资产范围限制，联网失败不丢弃平台证据。
`INGEST_SEARCH_RESULTS` 仍是入库唯一部署开关，默认 false。

候选资料与最终引用分开：本地最多 30 个候选，另为网页预留 10 个；同一 normalized ref 跨条件去重，
正文读取补全原引用，标注 metadata/content 证据级别。回答下方只列有效且被正文实际引用的来源，
编号保持稳定；审计同时记录 candidate_source_count 与 citation_count。引用抽屉复用现有
Console 认证正文接口，按需读取 Markdown，提供加载/无权限/失败/空正文状态并取消旧请求。
公开文档主题标签 EXISTS 必须关联当前 normalized ref，禁止其他资产标签造成错误命中。

## 2026-11-05 执行效率与引用展示补充

普通文档问题优先从已返回的 normalized ref 直接读取最多 3 份相关正文，省去单独的证据规划模型调用；
图谱、目录、章节和上下文类问题保留专用证据规划。正文不可用时，剩余预算内可回退一次实际返回目录/章节。
工具结果在合成阶段提供状态、条件、引用编号及聚合完整统计，正文只通过引用上下文传入一次；保留业务元数据、
日期和证据级别，不通过减少联网 10 条或缩短回答来获得耗时收益。现有审计增加单调时钟阶段耗时、
首段/总耗时、模型/HTTP 次数及输入字符数。此次不引入 HTTP 并发，不修改模型路由或覆盖 active Prompt。
少量实测存在模型波动，详见 [验证记录](review/query_latency_optimization_review.md)，不承诺固定完成时限。

展开的引用卡片正文最多显示 6 行，保持自然卡片高度；抽屉继续预览内容，移除平台资产导航，保留安全的
“打开网络资源”外链。输入框上方不再显示本页记录说明。
