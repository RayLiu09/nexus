1. 结论摘要

岗位分析的核心不是把招聘标题直接映射到预设岗位，而是从清洗去重后的真实企业岗位提取六要素任务事实，依据任务相关度和相似度合并形成标准岗位，再用国家职业大典等权威标准校核边界，沉淀可供专业建设方案等下游应用使用的工作内容和技能要求。系统必须把原始证据、机器结果和人工结论分层保存。

处理主线

清洗 → 去重 → 任务提取 → 聚类/分类 → 词典治理。每一步都有独立输入输出、运行版本和质量门禁，允许从任一步幂等重跑。

证据优先级

职责文本是岗位分类主要证据，工作对象、场景、工艺和工具是边界证据，标题只是弱证据。上游查询词和来源标签不得直接决定岗位类别。

技术策略

确定采用规则与统计模型完成确定性处理，采用结构化大模型完成六要素语义抽取，采用密度聚类生成候选类别，最终由版本化词典和人工审核控制正式结果。

四项必须坚持的业务规则：（1）原始文本永不覆盖；（2）职责证据优先于标题；（3）同一岗位允许主类别＋次类别；（4）正式结果只使用有效、去重、已归类并通过边界校验的记录。

2. 处理边界与输入输出契约

本文不设计招聘网站抓取、关键词生成、抓取轮次、岗位规模分析和外层应用编排。上游只要按统一契约提交岗位记录，本处理模块即可独立运行。

字段语义边界：job-detail-summary__tags 的经验/学历字段、job-description__tags .job-description__tag 的技能字段和 job-detail-summary__company-meta 的企业属性分别进入对应统一字段；字段映射、类型校验和缺失标记由配置化接入适配器完成。

接入规则

  • 以采集端 recordId 和 Provider 作为重放幂等键，不以分页顺序生成岗位主键。
  • 同一记录 ID 的重复响应跳过；相同 ID 若返回不同内容则报告契约错误，不覆盖原始岗位。
  • 上游终态后逐页读取；一页岗位记录与本地分页游标在同一短事务提交，外部 HTTP 请求不在事务内。

  • 清洗、缺失标记和技能拆分属于后续处理，不覆盖原始岗位值。

2.1.3 原始岗位信息留存与统计基线

同步接入的原始岗位信息必须长期保存，不能只保留清洗后的投影。raw_jobs 是后续处理和原始数据统计的起点；同一来源岗位出现新的采集记录 ID 时新增原始版本，不因重新清洗、去重或分类而覆盖。

对象关键字段存储规则
raw_jobsid、title_raw、company_name_raw、description_raw、responsibilities_raw、requirements_raw 等岗位原值列按实际 fields 结构保存岗位数据；不混入采集状态、查询参数和来源页。
raw_job_provenanceraw_job_id、provider_code、upstream_record_id、source_job_id、source_url、collected_at、raw_record与原始岗位一对一，保存采集出处和完整响应；同一上游记录 ID 幂等，同一来源岗位的新记录 ID 保留新版本。
dataset_snapshotsnapshot_id、source_scope、cutoff_at、raw_record_count、snapshot_hash、status后续处理选择原始岗位形成完整数据集快照；不以单次同步运行充当分析范围。
统计口径：raw_jobs 行数是原始采集记录版本数；来源岗位数和去重后的需求实体数由后续身份判定分别计算。数据集快照是分析处理单位，不能把一次同步运行直接计为岗位需求量。
字段组必需字段规则
来源身份source_name、source_job_id 或稳定源记录键、source_url、crawled_at用于硬去重和证据回溯；来源 ID 缺失时，上游必须给出可复现的稳定键。
岗位主体title_raw、company_raw、region_raw保留源值；允许标准字段为空，但必须记录缺失原因。
岗位文本description_raw、responsibility_raw、requirement_raw、bonus_raw职责、任职要求和加分项拆分字段是常规处理主输入；description_raw 作为完整原文用于验证、证据回溯和拆分异常时的兜底解析，并保留原文 offset。
辅助属性发布时间、薪资、学历、经验、行业、雇佣类型用于有效性、去重和分类边界；不作为任务事实的替代证据。
追踪信息raw_job_id、来源身份、上游扩展字段保存在采集出处中，只表达来源，不直接作为岗位类别标签。
边界说明：接入适配器先完成响应校验、原始岗位持久化和来源追踪；后续再按处理范围构建数据集快照并进入清洗、去重和任务分析。原始响应访问必须按权限隔离。

3. 内部处理链路与状态

3.1 完整数据集快照处理 DAG

快照固化完整数据集 / cutoff / hash
→
文本清洗全量字段标准化与职责分区
→
全量重复消解跨采集记录、来源和地区比较
→
任务抽取六要素＋证据 span
→
聚类/分类全量候选簇＋正式类别
→
词典候选审核、发布、版本化

原始岗位接入只负责可靠写入 raw_jobs 及其采集出处；处理链路以完整 dataset_snapshot 为输入。清洗、去重、任务抽取、聚类和分类必须在同一快照范围内运行，不能按单次同步运行分别生成局部结果后直接拼接。聚类和分类是两个不同动作：没有正式词典覆盖的任务进入无监督候选聚类；已有有效词典覆盖的岗位优先走规则＋语义原型分类。新簇经人工命名和标准校核后进入词典候选，词典发布后可触发受影响记录的重新分类，但不触发任何抓取动作。

3.1.1 快照边界与处理粒度

对象边界定义处理粒度
raw_jobs采集端一个 recordId 对应的原始岗位版本。原始接入与统计基线；采集出处通过一对一表追溯，不承担清洗和聚类状态。
dataset_snapshot / snapshot_id在 cutoff_at 时刻、指定 source_scope 和筛选条件下的完整岗位数据集，可覆盖多次采集得到的原始记录。作为清洗、全量去重、画像构建、岗位合并和标准岗位统计的统一边界；snapshot_id 不是一条岗位记录。
demand_id / posting_id快照中的一个岗位需求实体及其主处理记录。六要素抽取和 posting_task_profile/posting_skill_profile 以一条岗位需求为计算单位，每条记录独立生成事实和画像。
standard_job同一快照内多个岗位需求画像合并形成的标准岗位候选或正式岗位。只有在全量岗位画像生成后，才跨 demand_id 计算相似度、聚类和成员归属。
边界原则：六要素抽取是“快照范围内逐岗位执行”的行级任务；岗位归一化、标准岗位合并和需求统计是“完整快照范围内”的集合级任务。不能把一次同步运行当作一个快照，也不能在六要素抽取阶段提前跨岗位合并。

3.2 处理状态

对象状态状态含义与门禁
岗位记录valid / invalid / insufficient失效或职责信息不足的记录保留在原始数据集中，但不进入任务抽取和类别统计。
重复决策unique / duplicate / possible_duplicate / reviewed在完整数据集快照内进行全量比较；高概率重复自动成组，灰区必须复核；不同地区不得仅因模板相同自动合并。
任务事实candidate / accepted / review_required / rejected必须具有原文 span；无证据、字段越界、模型低置信度进入复核。
岗位分类classified / multi_class / review_required / excluded / unclassified保存主类和可选次类；强排除记录原因；未知类别进入聚类候选。
词典版本draft / in_review / active / retired同一专业范围只能有一个 active 版本；发布后内容不可原地修改。
幂等要求：相同 snapshot_hash + processor_version + dictionary_version 必须复用已有成功结果；规则、模型或词典变化时创建新运行，不覆盖历史证据。上游 recordId 的重传幂等属于接入层，不能替代数据集快照级幂等。

4. 文本清洗与去重设计

清洗的目标是让字段可比较、可验证、可检索，而不是把招聘原文改写成“漂亮文本”。章节拆分由爬虫引擎提供；本模块验证拆分结果并在异常时兜底。所有清洗结果都必须与原文并存。

4.1 字段级文本模型

当前同步数据是字段化 JSON，岗位字段已经是纯文本，岗位职责、任职要求和加分项已经由爬虫引擎拆分输出。归一化模块不重新承担章节拆分；清洗器负责字段规范化、拆分结果与完整 description 的一致性验证，并保留原始 JSON。只有拆分字段缺失、为空或无法与原文证据对应时，才启用有限的 description 兜底解析。

层次内容用途
raw_payload完整同步 JSON 和字段原值，包括标题、薪资、技能标签、地址、企业属性、拆分后的职责/要求/加分项及 description 原文；原始换行和标点不可变。历史统计、审计、回溯、重新处理和争议复核。
clean_fields按字段生成的规范化值：标题、企业、地区、薪资、技能集合以及爬虫拆分后的职责/要求/加分项文本；不丢失字段级缺失状态。全量去重、质量校验、任务抽取和规则匹配。
analysis_segments优先由上游拆分字段转换得到的章节、条目、句子和任务/要求 span；附完整 description 的原文 offset、标准词、来源字段和版本。任务抽取、向量化、分类证据和人工审核。

4.2 纯文本字段清洗规则

1
JSON 类型和缺失语义。先按配置化 schema 校验字段类型；null、空字符串和空数组保留原值，同时生成 missing_fields，不把缺失推断为“学历不限”“全职”或其他业务值。
2
编码与 Unicode。使用 ftfy 修复乱码，执行 Unicode NFKC；统一全角/半角标点、不可见字符、连续空格和换行，但保留原文字符 offset。繁简转换只作为检索别名，不覆盖专业词。
3
标题清洗。保留原始标题；仅移除可被正则确定为职位编号的后缀（如 (MJ000966)）、抓取装饰和地区/急聘标记。语义括号（如 平台软件工程师（Agent开发））保留，职级和技术方向不得删除。
4
拆分字段校验。以爬虫输出的职责、任职要求和加分项字段作为主处理输入；检查字段是否存在、条目是否完整、章节顺序是否合理，并将每条内容回指到完整 description 的原文 offset。发现缺失或无法对齐时标记 section_validation_failed，再进入有限兜底。
5
description 保留与兜底。对完整 description 只做纯文本规范化和证据索引，不作为常规章节拆分输入。仅当拆分字段缺失、为空、结构损坏或无法回指原文时，按标题行、编号列表和能力触发词执行兜底分段，并将 fallback_parser=true 写入运行结果。
6
薪资字段解析。保留 2-3.5万·15薪 等原值；使用 Decimal 和受限正则拆出下限、上限、币种、单位、发薪月数和面议状态。月薪等价值只作为统计派生列，不能覆盖 salary_raw 或丢失 15 薪信息。
7
技能标签清洗。对 skillsText、jobTagsText 按逗号、顿号、分号和换行拆分，保留 source_field；斜杠只在标签语境下作为分隔符，技术名称内部斜杠（如 SQL/NoSQL）保留并生成别名关系。
8
地址和企业字段。地址保留原文并用行政区字典生成省/市/区候选；企业名称只去除比较噪声并保留法人、分公司等主体信息。行业、规模、融资字段按正式映射进入 typed columns，不从其他字段猜测。
9
分析副本脱敏。电话、微信、邮箱等仅在送入模型和日志的分析副本中脱敏；原始 JSON 和统计所需字段仍按权限保存，避免清洗影响历史统计。

4.2.1 描述字段验证与兜底规则

description 是同步过来的完整岗位说明原文，保留它是为了下游信息验证、证据回溯和拆分字段异常时的兜底解析。常规处理直接消费爬虫已拆分的职责、任职要求和加分项字段；description 不重复承担正常章节拆解。skillsText、jobTagsText、学历和经验字段只能作为补充或交叉校验，不能覆盖拆分字段中的明确要求。

规范章节上游字段语义与兜底识别规则输出对象业务约束
overview爬虫拆分的岗位描述/职位简介/工作概述字段；必要时用 description 原文校验。description_section，可产生场景和方向候选。只作为背景证据；含有明确动作时才产生任务候选。
responsibility岗位职责、工作职责、工作内容、主要职责、负责事项；包括编号列表、项目符号和同一主语下的并列动作。task_fact（实际执行任务）以及六要素证据。是岗位聚类的最高权重来源；动作＋对象不足时只能保留候选并标记缺失。

unknown拆分字段缺失、无法与 description 对齐，或兜底标题/列表结构损坏。保留原文的未知段、section_validation_failed 和 fallback_parser 标记。不丢弃、不强行归类；涉及核心内容时进入 review_required。
  1. 主流程直接读取爬虫拆分字段，并为每个章节和条目建立到完整 description 的字符或行号定位；优先使用上游的章节类型和条目顺序。
  2. 校验拆分字段是否覆盖原文核心段落、是否发生重复、是否出现职责内容落入要求字段等冲突；只记录校验结果，不重新改写上游拆分结果。
  3. 拆分字段缺失或无法对齐时才启用兜底：按纯文本换行、标题词、编号列表和能力触发词识别章节；标题可带序号、冒号、空格、中英文括号或“（非必须）”标记。
  4. 兜底模式下，同一章节按编号、项目符号、分号和句号切成最小条目；并列动词拆出子任务，保存原句、顺序和父条目 ID。
  5. 无论主流程还是兜底流程，每个 section、item 和 fact 都必须保存 source_start、source_end、原文片段、来源字段、解析器版本和置信度；归一化短语必须能回指 description 原文。
样本使用方式：该岗位的职责、任职要求和“加分项（非必须）”优先采用爬虫拆分字段生成 task_fact 与 requirement_fact；完整 description 用于验证“Agent 系统与算法平台的工程实现”“Python / Java / Go / Node.js”等条目是否有原文证据。只有拆分字段缺失或无法定位时，才从这段 description 兜底恢复，不把正常流程重复执行一遍。

4.3 硬去重与软去重

类型判定条件主记录选择保留信息
hard同一数据源的相同岗位 ID、规范化 URL 或同一原始记录版本；无 ID 时使用稳定 source_record_key / 内容哈希。字段完整度最高、发布时间最新者；并列时以抓取时间最新者为主。所有原始岗位版本保留去重原因和快照追踪，不删除历史记录。
fingerprint由 source_name、source_job_id/source_url、title_normalized、company_normalized、region_normalized 和 description 分段哈希组成；同一原始输入在不同运行中保持一致。写入处理域的 exact_fingerprint，算法版本随运行快照保存。可重跑、可审计；原始采集记录统计以 raw_job_id 为基线。
soft完整数据集快照内先按来源/企业/地区候选 blocking，再比较标准化标题、职责拆分文本、任职要求/加分项集合、技能集合、地址和时间；使用字符 n-gram、集合相似度和必要的向量特征估计匹配概率。优先职责字段完整、描述证据完整、发布时间最新、字段缺失少且来源可访问者。保留 dedup_group_id、匹配概率、各字段贡献、snapshot_id 和主记录理由；不得物理删除。
near_duplicate同一企业发布模板相同但地区、职级、技能组合或招聘时间窗口不同；职责相似但业务需求可能独立。不自动合并统计实体，进入“同模板不同岗位”标记或人工复核。避免把同企多地真实需求或同标题不同方向压成一个岗位。
不要这样做：不能只按岗位标题去重，不能把所有缺失企业名的记录视为同一企业，不能因文本相似就删除跨地区真实需求，也不能用关键词命中数量直接当岗位需求量。
去重实现定案：软去重统一由 Splink + DuckDB 执行。MinHash/SimHash 不作为独立决策器；如需处理超长职责文本，只作为 Splink 的一个比较特征，最终概率仍由企业、标题、地区、时间和职责证据共同决定。

5.3.1 抽取执行算法与门禁

输入门禁

  1. 只读取同一 snapshot_id 下清洗成功且去重决策为 unique 或主记录的岗位；重复成员、失效记录和没有职责证据的记录不进入六要素正式抽取。
  2. 抽取输入固定为 responsibility_raw、requirement_raw、bonus_raw、skill_tags_raw 和结构化字段；完整 description_raw 仅用于证据验证或兜底。
  3. 每个输入锁定 cleaning_run_id、dedup_group_id、primary_posting_id 和 snapshot_hash，保证抽取与清洗去重结果一致。

候选到事实

  1. HanLP 做中文分句、词性/依存分析和技术实体候选；规则词典识别动作触发词、对象、工具、工艺、场景和成果模式。
  2. 对“负责 A 与 B 的实现和维护”这类并列结构做依存关系展开，生成多个动作—对象候选，但保留同一父句和共享条件。
  3. 规则无法确定关系时才调用 LiteLLM 结构化抽取；模型只能在候选句和允许字段内补足关系，不能引入句外常识。
  4. 将每个候选组装为一条原子任务事实；工具、方法和场景没有证据时保持空值，不用标题或公司行业强行补全。

标准化先精确别名匹配，再做限定范围的模糊匹配；动作、对象、工艺和工具分别使用对应词典，不允许跨类型最近邻替换。canonical_id、alias_id、normalization_method
事实门禁要求动作＋对象至少一组证据；每个非空要素必须有原文 span；去重主记录、章节来源和快照版本必须可回溯。accepted / review_required / rejected task_fact
置信度计算：采用可配置加权分数而不是直接使用模型概率：证据 span 完整性、规则命中、词典归一可信度、模型结构化置信度和字段冲突惩罚共同计算 fact_confidence。阈值由金标集校准；高于自动采纳阈值进入 accepted，中间区间进入复核，低于拒绝阈值只保留候选。阈值、权重和版本写入 extraction_run，不得硬编码在结果中。

5.3.2 canonical_id 生成与任务聚合键

canonical_id 不是原文字符串的直接 hash，也不是向量近邻得到的 topic ID，而是“要素类型＋版本化术语登记＋别名关系”生成的稳定概念 ID。它用于单岗位任务项标准化和跨岗位相似度计算，但不能改变或删除原始 task_fact。

步骤规则约束
表面归一Unicode NFKC、大小写、空白、标点、常见缩写统一；保留 raw_term 和 evidence span。AGENT开发 可归一为 agent开发，不删除技术限定词。
类型确定先判定 action、object、tool、method、context、output_constraint 或 skill。Docker 和“容器化”不能因为相似而共用一个概念 ID。
精确词典在同一类型、专业范围的 preferred_label、alias、缩写表中精确命中。别名指向同一 concept_id，但保留 alias_id 和来源。
受限模糊匹配仅在同类型候选词表内使用编辑距离/别名相似度；低于阈值进入复核。禁止跨类型最近邻替换，禁止用 embedding 直接发放正式 ID。
未知概念生成 candidate:{type}:{sha256(normalized_surface)} 临时 ID，进入长尾候选；审核后分配稳定 {namespace}.{slug}。临时 ID 不能直接参与正式标准岗位发布；批准后保留旧 ID 到正式 ID 的映射。
版本治理显示名称修改不改变 concept_id；概念拆分/合并通过新版本和 replaced_by/broader 关系处理。历史 task_fact/profile 保留旧 ID 和旧词典版本，不能原地改写。
要素专属规则：action 归一动词词干并去掉“负责/参与”等语气词；object 保留业务限定词和实体层级；method 与 tool 分开建词典；context 按行业、地点、生产环节和业务场景分层；output_constraint 保存成果类型、操作符、数值和单位。

单岗位任务键：对一个 accepted task_fact 使用 task_key = sha256(action_id | sort(object_ids) | sort(tool_ids) | sort(method_ids) | sort(context_ids) | sort(output_ids)) 保存关系结构。该键只用于同一岗位内部索引、重复出现标记和跨岗位相似度计算；posting_task_profile 不据此删除重复事实，跨岗位支持度只在 standard_job_task 阶段计算。

5.5 岗位级任务画像与技能画像

这里的“岗位画像”是单个 demand_id/posting_id 的抽取结果投影，不是跨岗位统计结果。task_fact 保存不可变的原子事实和证据，posting_task_profile 只负责把这些事实按原文顺序物化为一个岗位的任务项集合；它不负责跨岗位去重、合并或计算核心任务频次。跨岗位的相似度、支持度和标准任务统计推迟到 standard_job 候选形成并确定成员之后。

画像构建规则下游用途
posting_task_profile一条岗位需求生成一个画像；逐条保存任务事实的原文顺序、六要素 raw/canonical 值、证据 span、任务关系、置信度、状态和任务向量引用。accepted 任务进入正式相似度向量；review_required 保留在画像中作为待审事实但不进入正式统计向量；rejected 只保留在事实审计链，不进入画像任务项。相同文本或相同 canonical 组合重复出现时保留 occurrence，不静默删除。作为完整数据集范围内岗位相似度、聚类和标准岗位成员判定的输入。
posting_skill_profile一条岗位需求生成一个画像；保存 must/bonus、技能标签和有证据的任务工具/方法及其来源、置信度和权重。仅在该岗位内部合并同一技能的来源并保留来源集合，不跨岗位求并集或计算支持度。作为标准岗位技能归纳和单岗位技能要求展示的输入。
posting_context_profile一条岗位需求的场景、行业、地区、业务对象和边界标记；保留原始来源和证据，不把企业行业直接提升为任务事实。作为完整数据集范围内的边界约束和标准岗位合并校验。
对“只聚合 accepted task_fact；按 canonical_id 去重，计算核心任务频次”的正确解释：这句话不能作为 posting_task_profile 的生成规则。它应拆成两个阶段：第一，岗位画像阶段只读取并物化该岗位的任务事实，保留每次 occurrence；第二，在 standard_job_member 已确定后，standard_job_task 才以 accepted task_fact 为正式统计输入，按任务概念组合计算跨岗位 demand 支持数、企业支持数、频次、权重和核心/补充角色。canonical_id 只作为概念对齐和统计键，不是删除原子事实的依据；同一岗位出现两次不会制造两个岗位支持，多个岗位各出现一次才形成两个 demand 支持。

company_support_count = COUNT(DISTINCT company_id WHERE task_unit)
occurrence_frequency = COUNT(task_fact_id WHERE task_unit)

5.6 与既有领域项的映射

任务项不得回写旧领域表；直接写入处理域的 task_fact 和 requirement_fact。建议 fact_type 至少区分 work_taskprofessional_skilltoolprocess_methodcertificateprofessional_literacy；要求事实另带 requirement_level=must|bonus、source_section=requirement|bonus。每项保留 posting_id、规则版本、Prompt 版本、置信度和 raw evidence。技能与职业素养不得混为同一类别，要求事实不得伪装成工作任务。

6. 岗位任务聚类设计

聚类对象是六要素抽取后形成的 posting_task_profile，核心输入为“标准化任务短语＋工作对象＋工艺/设备＋场景”，不是岗位标题或技能标签。聚类先生成候选簇，再由业务规则和人工金标命名；算法不能直接把簇名当作正式岗位类别。岗位归一化使用任务画像，岗位技能计算使用独立的 posting_skill_profile，两者不能混成一个向量。

6.1 特征与约束

特征层组成作用
语义特征任务短语和职责句向量；中文模型优先使用 bge-large-zh-v1.5，可在本地批量生成。识别“样品采集/现场取样”等表达差异，形成候选相似关系。
结构特征动作、对象、场景、工艺、工具 canonical ID 的多热/稀疏特征。避免纯语义把“食品化验”和“水质分析”错误合并。
边界特征专业方向、行业、地区、强排除词、岗位类型。作为硬约束或惩罚项，防止跨专业/跨行业漂移。
标题特征标题及别名只作低权重辅助；同一标题的不同职责允许进入不同簇。解释企业叫法，但不主导类别。

6.2 候选簇生成与合并规则

推荐流程

  1. 按专业方向和有效性过滤，排除职责缺失、强排除和明显失效记录。
  2. 对任务要素 canonicalize，生成向量和结构特征。
  3. 使用 HDBSCAN/层次聚类生成候选簇；不预设固定簇数，允许噪声点。
  4. 对边界簇用成对相似度、规则冲突和人工样本复核。
  5. 相同动作＋对象高度相似且场景一致时合并；对象或工艺差异造成业务边界时拆分。

命名原则

  • 名称采用企业常见、可理解的岗位类别，如“环境监测采样岗”“水处理运行岗”。
  • 名称体现主要工作对象或核心过程，不以单一设备名替代岗位。
  • 保留簇内企业标题作为别名词典，不强制企业标题统一。
  • 同一记录可以主类别＋次类别；主类用于主统计，次类用于能力覆盖分析。
  • 无法形成稳定簇的长尾任务进入“待命名/扩展岗位”，不被强行归入最近类别。

不能只看 silhouette 等无监督指标。每个候选簇应同时输出：簇内样本数、核心/边界/噪声样本、代表任务、代表标题、主要对象/工艺、跨专业冲突、与其他簇的最近邻和人工标签。业务专家至少复核高频簇、边界簇、混合职责簇和长尾簇，形成可计算的拆分/合并金标集。

7. 标准词典构建与生效

正式词典是“真实任务事实归纳结果＋权威标准边界校核＋人工审核”的版本化规则资产。国家职业名称用于统一口径和边界校核，不替换企业岗位名称，也不承担企业岗位分类的唯一命名责任。

7.4 标准岗位库与国家职业大典核验

标准岗位库中的岗位是由真实企业岗位任务归纳形成的应用对象，不等同于招聘标题，也不直接等同于国家职业大典名称。每个标准岗位必须同时具备标准名称、岗位定义、核心工作内容、技能要求、适用场景、正例/边界例/排除例和来源岗位集合。

标准岗位对象内容下游可用方式
standard_job稳定岗位 ID、标准名称、岗位定义、任务原型、技能原型、场景边界、状态和版本。专业建设方案、课程/能力映射、岗位需求统计和岗位画像查询。
standard_job_task来自高置信度任务画像的核心/补充任务、动作—对象—工艺—成果关系和代表证据。展示岗位工作内容、课程任务映射和岗位间任务比较。
standard_job_skillmust/bonus 技能、工具、工艺、证书和职业素养，保存来源岗位数、证据覆盖率和权重。岗位技能要求、专业技能缺口和人才培养目标计算。
occupation_reference国家职业大典或其他权威标准的职业编码、名称、版本、核验结论和差异说明。作为边界和口径核验；允许“无直接对应/部分对应”，不强行替换企业标准岗位名。
核验原则：先依据企业岗位任务形成标准岗位，再用国家职业大典、职业标准和技能标准核验其职责边界、职业归属和名称关系。核验结果至少区分 direct_match、partial_match、related、no_match，并保存匹配证据和人工结论。

8.1.1 多个原始岗位版本的同一需求判定

“原始记录相同”与“岗位需求相同”分为两层：raw_jobs.id 标识一条不可变采集记录，demand_id 标识同一来源下持续存在的岗位需求。岗位内容更新、薪资变化或描述补全对应新的原始岗位版本，通常不新增需求；岗位 ID 被来源复用、主体或地点发生实质变化时才拆分为新的 demand。

判定顺序规则结果
1. 来源主键同一 source_scope + source_job_id，且来源未标记 ID 复用。归入同一 demand；内容变化保留为新原始版本。
2. 稳定 URL无岗位 ID 时，规范化 URL 相同且企业主体、地区没有强冲突。归入同一 demand；记录 URL 证据。
3. 字段指纹无 ID/URL 时，对 source、企业主体、地区、规范化标题、职责拆分文本生成稳定 fingerprint；不使用数组行号。指纹完全一致可自动归并；近似指纹进入概率链接。
4. 时间连续性比较首次/最近采集时间、岗位有效状态、薪资和描述变化；同一 ID 长期消失后以完全不同标题/地点重新出现，视为 ID 复用候选。连续版本归并；复用疑点拆分或人工复核。
5. 概率链接Splink 在企业、地区、标题、职责/要求文本、地址和时间窗口内计算概率；相同模板但不同地区或职级默认不合并。高概率且无冲突自动链接；灰区进入人工复核。
6. 跨来源关系不同来源的相似岗位不直接共用 demand_id；另建跨来源链接，供标准岗位归并和去重统计选择口径。保留来源事实，避免跨平台重复被误当作同一来源需求。
统计口径：同一来源同一 demand_id 在一个数据集快照中计为一个岗位需求；多个原始版本保留历史变化。跨来源相似岗位默认分别保留，通过 standard_job_member 归入同一标准岗位；只有经过明确跨来源去重规则或人工确认，才在总需求统计中折算为一个跨来源需求。
事实与画像一致性约束：task_fact、requirement_fact 和各类 profile 必须外键关联 snapshot_id、posting_id 与 processing_run；同一快照、同一岗位、同一抽取/词典版本下，以 task_key 或 profile_hash 保证幂等。画像只读取最终 accepted 事实，生成后不可原地修改；重新抽取或词典变更必须生成新版本并保留旧画像，以便岗位归一化和技能统计回放。

9. 确定的开源技术方案

以下不是候选清单，而是建议的主实现组合。各库承担不同的业务职责，替换必须通过同一接口和金标集验证；没有必要的库不纳入 P0 依赖。

业务能力确定选型具体实现不采用的方案与原因
文本清洗ftfy + regex + Pydantic v2Pydantic 校验字段化 JSON 和拆分字段契约；ftfy 修复乱码；regex 配合 Python unicodedata、decimal 完成 Unicode、标题编号、纯文本列表、薪资和联系方式规则。清洗函数输出字段规范值、拆分字段校验结果、原文 offset 和兜底标记。不把 trafilatura/lxml 作为主流程：当前输入没有 HTML 结构，DOM 正文抽取会引入无效假设；不依赖 LLM 清洗，避免结果漂移。
岗位去重Splink + DuckDB用 Splink 建立可解释的概率实体链接：先按来源、地区和企业标准名 blocking，再比较标题、公司、职责字符 n-gram、发布时间和 URL；DuckDB 承担批处理，rapidfuzz 作为字符串 comparator。输出匹配概率、字段贡献和主记录。不把单一 SimHash/MinHash 当最终去重：只能说明文本近似，不能解释企业、地区和发布时间的组合；不使用黑盒向量近邻直接合并。
任务抽取HanLP 2.x + LiteLLM 结构化抽取 + Pydantic v2HanLP 做中文分句、词法、依存和实体候选；LiteLLM 调用统一模型完成动作—对象—工具—工艺—场景—成果六要素的困难语义解析；Pydantic 严格校验 JSON、字段白名单和证据 span。规则抽取优先覆盖明显列表项，模型只补充复杂关系。不采用纯关键词正则：无法处理并列动作和隐含对象；不采用纯 LLM：难以保证证据约束、稳定格式和成本可控。
任务聚类BERTopic（BGE 中文向量 + HDBSCAN）sentence-transformers 加载 bge-large-zh-v1.5 生成任务向量；BERTopic 使用 HDBSCAN 发现未知簇、c-TF-IDF 生成代表词；保留噪声点和簇概率。聚类输入是任务短语及六要素拼接文本，不是岗位标题。不使用 K-Means 作为主算法：必须预设簇数且会强行吸收长尾；不使用 UMAP 坐标直接做业务判断，降维只用于诊断。
已知类别分类规则评分 + BGE 原型相似度 + scikit-learn 校准词典规则先执行强排除和必须条件；再将岗位任务向量与类别 prototype_tasks 做余弦相似度；有足够人工金标后用 scikit-learn LogisticRegression/CalibratedClassifier 校准置信度。输出主类、次类、分值和命中证据。不直接使用 BERTopic topic ID 作为类别：topic 不稳定、不可审计；不在金标不足时训练复杂监督模型。
词典治理SKOS + RDFLib + pySHACL岗位类别、别名、任务词、工艺、工具和场景建模为 SKOS concept；RDFLib 负责 JSON-LD/Turtle 读写和版本快照；pySHACL 校验每个概念必需标签、关系、排除规则和证据引用；正式快照仍存 PostgreSQL。不引入独立图数据库：词典规模和查询复杂度不足以抵消运维成本；不把自由 Markdown/Excel 作为规则真源。
P0 固定组合：ftfy + regex + Pydantic；Splink + DuckDB；HanLP + LiteLLM + Pydantic；BERTopic + BGE + HDBSCAN；规则评分 + 原型相似度 + scikit-learn 校准；SKOS + RDFLib + pySHACL。库版本、模型版本和许可证写入处理运行清单。

10.2 人工复核优先级

P0 错误边界

强排除争议、跨专业误纳入、可能造成统计方向错误的记录。

P1 混合职责

一个岗位同时承担多个类别任务，需要主类/次类决策。

P2 证据不足

模型输出无法定位 span、任务要素不完整或分类置信度不稳定。

P3 新概念

新工艺、新设备、新企业称谓和新任务进入词典候选。

10.3 安全边界

  • 电话、微信、邮箱等联系方式在送入模型前脱敏；日志只保留 posting_id、run_id、trace_id 和规则摘要。
  • 任务抽取结果必须经过 JSON Schema、字段白名单、证据 span、置信度阈值和人工状态机，不得直接变成正式类别。
  • 词典规则使用受限 DSL 或 SKOS 属性，不接受任意 Python、SQL 或脚本执行。
  • 岗位原文、清洗快照和证据接口按组织权限读取；机器结果和人工结论均保留审计链。

11.1 最小测试集

  • 同一标题但职责分别为“现场采样”和“污水设备巡检”的记录得到不同任务事实和类别。
  • 食品化验、医学采样、服务器运维等强排除样本不会因为泛化标题命中而进入专业类别。
  • 同企同岗同地区重复被合并；同企不同地区同模板岗位不被错误合并。
  • 并列职责可以拆出多个动作和对象；“熟悉 Excel”等任职要求不会被生成实际工作任务。
  • 无 evidence span、低置信度、弱排除和混合职责样本进入人工队列。
  • 聚类重复运行结果可比较；词典激活后分类可复现，退役版本仍可查询历史结果。
