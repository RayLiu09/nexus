# 资产中心职业能力分析：三种图谱视图满足度与优化建议

日期：2026-10-27。范围：当前工作区代码、已有本地样例，以及实际数据库全部 14 份职业能力分析对应的标准化记录与原始工作簿。本报告为建议，尚未修改正式产品契约或实现新视图。

用户补充边界：ability-atlas 仅用于参考树图、旭日图、矩形树图的形态和构建逻辑，不导入其样本数据、不将其作为资产中心的数据来源。允许补齐平台领域模型，但必须先用已存在的 14 份数据验证可解析性。

## 结论

当前仅具备部分可复用数据与交互基础，尚未满足“树图 → 旭日图 → 矩形树图共享同一棵层级树”的要求。需要统一层级读模型，再增加三种渲染方式。现有“能力树”是 Ant Design 目录树；“能力图谱”是默认筛选首个任务的 ECharts 力导关系图。二者不是同一份树数据的不同展示。

推荐保留列表中的“能力树”和“能力图谱”入口，让两者打开同一个图谱抽屉：前者直接选中“树图”，后者提供固定顺序的 `树图 / 旭日图 / 矩形树图`，默认树图。“树图”与“能力树”只是一种视图的两种入口命名。现有关系图不能作为树图的满足证据；本次三视图切换条不增加第四种类型。

## 推荐共享层级

```text
专业根节点
└─ 岗位类（来源缺失时为“未归类”）
   └─ 典型工作任务
      ├─ 通用能力 G → G 能力项
      ├─ 社会能力 S → S 能力项
      ├─ 发展能力 D → D 能力项
      └─ 工作内容 → P 能力项（可以有多个工作内容）
```

P 作为工作内容及其能力的类别属性和图例，目标树不再额外插入“职业能力 P”层。岗位类与能力类别必须区分；G/S/D 是任务下的能力分组。

共享树只构建一次，推荐节点包含：`id`、`kind`、`name`、`fullText`、`sourceId`、`categoryCode`、`children`、`abilityCount`。叶节点只有能力；结构节点的能力数量为全部子节点数量之和。节点 ID 使用原业务 ID 与稳定的分组命名空间，不使用数组下标，以便切换、筛选后保持定位。

渲染规则：

- 树图：ECharts `tree`，`orient=LR`，传入 `[root]`，展示专业根。
- 旭日图：ECharts `sunburst`，传入 `root.children`，岗位类是第一业务圈层，中心显示专业或当前钻取节点。
- 矩形树图：ECharts `treemap`，传入 `root.children`，以岗位类开始嵌套。

隐藏根节点只是显示差异，三种视图的业务节点 ID、父子关系和能力集合完全一致。渲染层不得分别分组、复制节点或解释业务归属。图表排序保持一致，关闭默认按值重排；任务/工作内容按 display_order、自然编号、稳定 ID 排序，任务下统一 G、S、D、工作内容顺序。

## 数据缺口与异常处理

实数据检查确认：14 份中只有 2 份有明确“岗位类／岗位类别”表头。其他文件虽有岗位描述，也不能因此认定其具备正式岗位分类及任务归属。岗位类暂缺时，可先使用明确标注的“未归类”显示分组，完成三视图展示。它是显示占位，不代表岗位类识别已完成；占位数不能标成“已识别岗位类数”。严格具备真实岗位类的完整验收，需要从来源证据中获取或经业务确认形成分类与任务归属。

目前解析器未投影岗位类，writer 将 task_description_structured 初始化为空；不能仅新增一个前端字段就宣称真实岗位类已补齐。若来源确有该信息，需覆盖标准化提取、领域存储、读取 API、历史数据处理与来源追溯。不要从专业教学标准或职业分类大典自动推断归属，也不要把一个任务复制进多个岗位类制造完整层级。

现有 `buildAbilityTree` 只展示匹配工作内容的能力，以及无 work_content_id 的 G/S/D。P 缺少工作内容、引用失配或未知类别时，可能无法进入目录树；P 包装层的统计仍可能包含这部分 P，存在“计数包含、叶节点未显示”的边界风险。这是代码路径分析，尚未验证实际资产是否存在这些异常。

统一构建应检查：任务/工作内容归属有效，每条能力恰好挂载一次，孤儿、重复和未知类别可追溯。异常数据不能静默丢失，也不能变成虚构的正式关系。可显示明确的异常清单；若采用“待确认工作内容”等占位，必须标记显示性质。显示层不得直接改变治理结论或版本状态。

## 数量与占比口径

- 每个有效能力叶节点权重为 1；工作内容、分组、任务、岗位类与专业根的权重为子树能力叶节点数。
- 同一条能力在树中只出现一次。G/S/D 不能为了表示应用于多个工作内容而重复挂载。
- 旭日扇区与矩形面积按能力项数量计算，不能使用任务数、内容字数、关系数或置信度作为面积。
- 无能力的任务/工作内容保留在共享数据模型中，abilityCount=0；树图可标记“0 项”，面积图不赋予虚假的正面积。不得照搬“无 children 就 value=1”的通用叶节点规则。
- Tooltip 显示能力数量、占父级比例、占当前筛选范围比例，明确分母。数量占比表示记录构成，不能解读为能力重要程度或熟练度。
- 完整资产范围下，根能力数应等于实际能力条目总数，并与 P+G+S+D 的精确分类统计对账；存在异常或未知分类时显式说明差额，不能强行修平。

## 页面与交互建议

统一抽屉顶部按 `树图 / 旭日图 / 矩形树图` 固定排序，不用响应式布局改变顺序。两个列表入口都挂载同一组件；切换视图只更新图表配置，不重新读取不同来源。

三视图共享筛选：默认建议“全部任务”，以体现从专业到岗位类的完整结构，同时保留任务筛选。该默认值与当前 SPEC/Prototype 的“首个任务”不同，应在实施任务包冻结并同步修改基线。若保留首任务默认，也必须三视图一致，清楚标明范围，并提供“全部任务”。岗位类筛选应与任务筛选联动，重置不再有效的任务选择。

切换视图保留筛选范围与选中业务节点；旭日/矩形钻取路径按节点 ID 保存。建议各视图保存自己的展开/钻取布局，复位只重置当前布局，筛选条件仍清楚显示。标签用来源短名或显示省略，完整原文保留在 Tooltip/详情中；不为图表切换重新调用 LLM。

树图支持缩放、平移、展开收起和适应画布；旭日图支持点击下钻与返回；矩形树图支持点击区块与面包屑。统一图例和配色，复用现有全屏与图片导出操作。密集标签通过钻取、合理画布高度和详情查看处理，能力数据不因图面拥挤被删减。

## 工程优化范围与可复用参考

最小落地方案复用现有 tasks（包含工作内容）与 ability-items 接口，按最多 200 条分页完整读取后，交给一个独立的层级构建模块，再交给一个统一图表组件。能力条目列表继续使用服务端分页。任务和能力读取失败或不完整时，不呈现完整数据占比。

现有 staging 图谱按节点类型有 1,200 节点、按边类型有 1,600 边的加载上限，不能直接把截断子图转为全资产面积分布。最小方案无须依赖 staging build 是否存在，也无须为新增两种图表重新抽取或重建领域关系。共享层级模块只组合已有事实，并明确标记显示分组；这需要更新原迁移任务包“浏览器不重新解释图谱事实”的边界说明。

若规模或岗位类需求超出前端组合能力，可再提供一个内部只读层级 API，返回来源标识、完整性标记、统计和树。它是消费读模型，不新增正式治理事实或冗余反向指针。读取范围应锚定同一 normalized_ref_id；避免并发重处理期间混合不同来源的数据。

仓库已有 `docs/e2e/ability-atlas/reference.md` 与 `assets/atlas-runtime.js`：按同一 data.tree 生成 tree/sunburst/treemap，树图 LR，面积图传 root.children。可参考其图表配置和全文提示设计。该参考还包含关系图，本次用户只要求三种视图，应以本次要求确定切换条。

只读核验现有电子商务师离线样例得到：1 个“未归类”占位、3 个任务、10 个工作内容、33 项能力（P21/G3/S6/D3），有 57 个图节点、56 条树边。此样例是本地派生文件，不是已纳入资产中心的资产，不能作为平台满足度证据；也不宜直接把离线 HTML 或整份全量 ECharts 脚本嵌入 Console。

## 后端补齐建议与 14 份数据验收边界

建议先冻结以下信息契约，再决定迁移形式，而不是增加一个无来源的岗位类字符串：

- 任务原文：保留 task_description 和对应的源 sheet/row/column；多行描述合并时保留分段与全部坐标。
- 来源岗位：增加 `job_roles`，保存原文岗位称谓、证据和提取状态，和正式岗位类区分。
- 岗位类：明确 category key/name、来源、任务唯一归属和证据；缺失保持 nullable，并由读模型提供“未归类”显示节点。若业务确认需要从岗位归纳分类，应将归纳结果和来源事实分开，提供复核与审计，不能直接作为解析事实自动落正式结果。
- 工作内容：按显式表头和编号建立 code/name/trace；支持 `1.1`、`A1` 与任务作用域内的 `1、2、3` 等编号方式。原表未给名称时才使用明确标记的显示回退，不覆盖原文事实。
- 能力身份：源 ability_code 作为原文展示编号保留，稳定业务身份应包含任务和来源条目。若放宽全分析编号唯一约束，需同步 writer 去重、关系、staging node_key、读取过滤和迁移；不能只删除一个数据库唯一约束。同任务重号仍须核验与质量处理。

历史修复应先为 14 份分别生成 dry-run 差异和对账报告，再按确认范围应用。对没有歧义的任务/工作内容/岗位描述修复应保留可保持的记录 ID、权限、normalized_ref 血缘与原编号；不能直接调用现有 delete-then-insert writer 重建全部分析，因为这会改变记录 ID，并可能令现有 staging source_id 失配。若需要修复标准化对象，必须保持对象内容、checksum、域投影与审计一致，不能只改数据库中的图表显示结果。

以 14 份数据作为固定验收集：所有源任务和能力行均有处理结果；每条能力为唯一有效记录、明确重复、待确认冲突或有据拒绝之一；全部工作内容有来源或明确回退；分类缺失可见；所有图表统计从同一有效能力集合计算。109/109 描述与工作内容声明可定位，只证明这些信息有源可取，不等于 14 份均能解析出无歧义的正式岗位类。严格要求“每份都具有真实岗位类且全部正式可用”时，现有源数据不能直接提供这一保证，需要补充分类规则或业务确认。
