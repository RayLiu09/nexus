## 第 2 页 — 项目背景

**我们要解决的问题**：

- 职业院校和企业积累了大量数据（政策文件、行业报告、岗位表、教材、教学标准等），但**格式各异、彼此孤立**，无法统一检索
- 用户问题往往是跨资产综合查询，比如"结合北京直播电商行业现状，为某高职规划电子商务专业建设方案"——但现有工具只能做关键词匹配
- 数据接入后缺少统一的质量标准——哪些可用？哪些需要人工复核？

**P0 阶段目标**：

> 将 9 类异构数据资产建成可统一语义检索、支持跨资产复杂问答、答案可追溯到原文的知识底座

**9 类资产**：产业政策 / 产业报告 / 行业报告 / 岗位需求数据 / 职业能力分析表 / 专业教学标准 / 专业布点数据 / 专业简介 / 电子商务类教材

## 第 4 页 — 知识加工：语义切块如何保证召回质量

> **核心认知**：切块是检索质量的第一道关。如果一段有意义的文字被错误切断、被噪声混入、或丢失了上下文标注，后续的 embedding 和检索都是"垃圾进、垃圾出"。

**我们的切块 → 召回质量链路**：

文档解析后的原始 blocks 是一堆粗粒度的段落/表格/图片片段。直接 embedding 会产生大量噪声。我们设计了一套 **10 道工序的精细化加工流水线**：

| 工序 | 真实处理内容 | 对召回的直接影响 |
|------|-------------|-----------------|
| **① 政策章节标题识别** | MinerU 有时把"（三）建设产教融合实训基地"识别为普通段落，用正则 `（[一二三四五六七八九十]+）` 提升为 heading | 恢复丢失的章节结构，支撑后续"命中一个 chunk 后返回整个章节"的扩展检索 |
| **② 指标卡片提取** | 报告中的 KPI 文字块（"同比增速 12.3%"）单独提取为 `metric_image` 类型 | 防止这类关键数据被后续步骤当作"短文本"删掉 |
| **③ 导航块剔除** | 去掉所有 heading/title 块 + `document_metadata` 标记块（标题/作者/日期已在资产元数据中） | 目录结构不混入检索内容 |
| **④ 无意义内容清洗** | 8 类噪声识别：页码（"第12页/共80页"、"Page 12 of 80"）/ 纯标点 / <4字短文本 / 二维码描述 / 宣传文案（"About Us"、"粉丝数 10w+"）/ 教材 CIP/ISBN 页 / 目录行 | 避免"第12页"作为检索结果返回 |
| **⑤ 图表归属归并** | 把"数据来源：商务部"、"图 3-2 行业趋势图"等说明文字归入相邻的 graph/table/image 块 | 图表说明不单独成块，与图表数据一起被检索 |
| **⑥ 跨页段落缝合** | 检测段落尾字不是句号/问号/感叹号等终止符 + 下一页首字不是数字/列表标记 → 跨页拼接，且只有跨 1 页的才合并 | 一段政策论述不会因为翻页被拆成两块 |
| **⑦ 缝合后噪声清洗** | `merge_continuation` 会把分散的版权碎片缝成长段落，用出版关键词（"策划编辑/责任校对/ISBN/开本/印张"等 30+ 关键词）命中 ≥2 个时移除 | 版权页不进入知识库 |
| **⑧ 行记录表分解** | 只对真正的行记录表（≥3列、≥2行数据、表头含"时间/部门/名称/内容"等记录关键词）拆成"表格概览 + N 行记录"；矩阵/交叉表保持完整 | 岗位表、布点表按行独立检索，而非 100 行混在一起 |
| **⑨ 章节路径注入** | 为每个语义单元构建 `heading_path`：向前扫描所有标题块，建立 h1→h2→h3 层级栈，更深标题折叠到 h3 | 检索命中块后，可沿 `heading_path` 溯回完整章节 |
| **⑩ 去重** | 同一文档内 >= 40 字的内容重复去除 | 避免多次检索到相同内容 |

**产出物**：每个 chunk 携带完整的 `locator` 追溯信息——`page_start/page_end`、`bbox`、`md_char_range`、`heading_path`、`source_block_ids`——回答可以直接引用到原文的具体位置。

## 第 5 页 — 切块质量的量化追踪

**质量报告——不是"感觉切得好"，而是"数据说了算"**：

每次知识加工完成后，自动对每份资产跑 7 个维度的定量检查，生成 Markdown 质量报告（只读，不修改数据）：

| 评估维度 | 指标举例 | 警告阈值 | 阻断阈值 |
|----------|---------|---------|---------|
| 结构覆盖 | 有多少 chunk 缺失 `heading_path`？ | > 20% | > 50% |
| 大小分布 | 最大 chunk 是否过长？ | 任意 > 2500 字 | > 5% 超标 |
| 边界风险 | 跨页缝合比例、跨标题误合并数 | 任一 > 0 | 待人工复核 |
| 噪声残留 | 目录型/版权型/页脚型/低信息块比例 | > 5% | > 15% |
| 表格处理 | 大表未分解数、行记录定位精度 | > 0 | 待人工复核 |
| 大纲覆盖 | 教材 chunk 是否挂到知识大纲节点 | 脱落 > 5% | 建议重建 |
| 检索就绪 | 综合判断是否可以投入检索 | — | block（不可用） |

**当前基线数据**（37 份资产 / 8,706 个 chunk）：
- **通过**：12 份 → 可直接投入检索
- **需优化**：17 份 → 已标记具体问题和建议修复方案（如"超大块需拆分"、"版本/出版噪声需加强过滤"）
- **需重建**：8 份 → 包括 0 chunk 的资产、heading 覆盖为 0% 的资产

## 第 6 页 — 不同资产，不同加工策略

9 类资产的性质差异巨大，不能一刀切。我们按资产特征设计了 4 类加工模式：

| 资产类型 | 加工策略 | 关键技术选择 | 为什么 |
|----------|---------|-------------|--------|
| 产业政策/产业报告/行业报告 | **语义切块** `semantic_repack` | 完整的 10 道工序；产出 `SEMANTIC_BLOCK` 类型 | 长文档，逻辑严密，需要保留章节层级和指标卡片 |
| 岗位需求数据/专业布点数据 | **逐行拆解** `row_decompose` | 表头作为字段名、每行一条独立记录 | 结构化表格，按行检索效率最高 |
| 专业教学标准/教材 | **语义切块 + 知识大纲 + 图谱** | `semantic_repack` 产出 chunk + 3 级知识大纲目录 + 知识点关系图谱 | 教材体量大、层次深，需要大纲导航和知识点关联 |
| 专业简介 | **板块拆解** `major_profile_decompose` | 按培养目标/课程体系/职业面向/能力要求等 6 大板块分解 | 结构固定，按板块独立检索 |
| 职业能力分析表 | **图谱提取** `graph_extract` + `tag_decompose` | 提取能力节点和层级关系 + 技能标签库 | 核心价值在能力体系，不在表格原文 |

## 第 7 页 — 检索架构：从"关键词匹配"到"意图驱动的多策略编排"

**v2.0 三层检索路由**：

```
用户提问："北京直播电商行业最缺哪些岗位能力？对应什么专业和课程？"
                                ↓
┌──────────────────────────────────────────────────────────┐
│ 第一层：意图理解                                           │
│ · 识别为 scenario_2 "结构化查询"                           │
│ · 抽取标签：region=北京, industry=直播电商                 │
│ · 路由守卫：检测到"专业"关键词 → 纠偏路由，防止误判          │
└──────────────────────────┬───────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│ 第二层：策略分派（并行执行）                                │
│ · 工具1：查岗位需求数据 → 北京+直播电商的岗位Top5和薪资分布  │
│ · 工具2：查职业能力分析表 → 这些岗位对应的能力要求图谱       │
│ · 工具3：查专业布点数据 → 北京哪些学校开了相关专业           │
│ · 最大并行度：4，超时/失败自动回退到兜底路径                │
└──────────────────────────┬───────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│ 第三层：证据链汇总                                         │
│ · 确定性模板组装：先能力图谱 → 再专业信息 → 再岗位数据       │
│ · 每个结论附引用来源（文档标题 + 章节位置 + 页码范围）        │
│ · Chart 占位符替换（ECharts 图表由后端拼接，非 LLM 生成）    │
│ · > ⚠ 生成比例监控（标记 LLM 产生的非引用内容）              │
└──────────────────────────────────────────────────────────┘
```

**5 类业务场景**：

| 场景 | 用户典型提问 | 分派策略 |
|------|-------------|---------|
| 讯息查询 | "2024 跨境电商政策有哪些？" | 语义搜索 → LLM 阅读总结 |
| 结构化查询 | "浙江省电商专业分布情况" | 数据库精确查询 + 多维度聚合 |
| 专业综合 | "高职电子商务培养目标" | 教学标准图谱 + 专业字段检索，双路合并 |
| 教材知识 | "短视频拍摄的具体步骤" | 教材语义搜索 + 章节大纲导航 + 题型自适应（8 种题型） |
| 检索无结果 | 未命中任何策略 | 自动回退到跨类型全库向量兜底 |

## 第 8 页 — 跨资产检索的关键技术：六层标签匹配

**业务挑战**：同一件事，不同资产用不同词汇——政策叫"直播电商产业"，岗位表叫"直播运营"，能力表叫"直播带货"，教材叫"直播营销"。

**我们的方案**：不依赖标准编码（PDF/Word 里几乎不会带 GB/T 编码），而是用**六层渐进匹配**：

| 层级 | 做什么 | 举例 | 依赖 |
|------|--------|------|------|
| L1 精确匹配 | 标签字面完全一致 | "北京市" = "北京市" ✅ | 无 |
| L1.5 规则归一 | 自动去掉后缀、括号、空白、全角半角转换 | "北京市" → "北京" ✅ | 无（纯代码，33 条规则） |
| L2 同义词 | 人工维护的别名表 | "直播带货" ≈ "直播电商" | 字典表（可为空） |
| L3 编码 | 标准编码匹配 | GB/T 2260 地区码 | 字典表（可为空） |
| L4 语义 | 向量相似度（HNSW, 512d） | "直播运营" ≈ "直播电商能力"（cos ≥ 0.75） | embedding 模型 |
| L5 全文兜底 | pgvector 全局搜索 | 以上全不命中 | pgvector 索引 |

**核心保障**：L1 + L1.5 + L4 三层不依赖任何字典和人工标注，即使完全无字典，方案仍然可用。L2/L3 是渐进增强。

**特殊处理**：ability（能力）类标签强制走 L4 + rerank。原因是不同资产来源的能力表述天然不同（"数据分析" / "数据分析能力" / "数据处理与分析"），只有语义匹配能覆盖。

## 第 9 页 — 回答质量保障：不只是"搜到"，还要"答对"

**检索到的 chunk 只是原材料，最终回答质量取决于三个关键增强**：

**1. 章节上下文扩展**（政策/报告类资产）

检索命中 1 个 chunk 后，沿 `heading_path` 反向查找其所属章节，把整个章节的内容一并返回给 LLM（上限 3 个章节 / 24 个 chunk / 12,000 字）。从返回"一句话"升级为返回"完整条款"。

例如：命中 chunk 在"三、税收优惠政策"下 → 自动返回完整章节标题和章节内全部 8 个 chunk。

**2. 答案模式自适应**（教材类资产）

自动识别 8 种用户提问类型，匹配不同的答案构建策略：

| 题型 | 识别特征 | 答案策略 |
|------|---------|---------|
| 定义型 | "什么是X"、"X的定义" | 返回概念定义段，紧凑边界 |
| 方法型 | "如何做"、"方法" | 返回方法论段落 |
| 过程型 | "步骤"、"流程" | 返回操作步骤序列 + 上下文前因后果 |
| 枚举型 | "有哪些"、"包括" | 展开枚举项，每一项单独标注 |
| 比较型 | "区别"、"对比" | 返回对比双方各自描述 |
| 完整章节 | "第X章" | 返回章节全部内容 |
| 综合问答 | 复合问题 | 多题型混合模式 |

**3. 弱证据过滤**

自动识别并降权以下内容类型：学习目标、目录行、知识回顾、章节引言、图表装饰文字。

**4. 重排序（rerank）**

`semantic_weight × 向量分 + tag_weight × 标签分`，对初排结果做二次排序，提升与查询意图最匹配的 chunk 排名。运行时可通过配置开关独立控制。

## 第 11 页 — 质量持续追踪与评价机制

**三个层次的"质量闭环"**：

**① Chunk 加工质量（知识入库前）**

每次知识加工后自动运行，7 维定量检查 → 生成质量报告 → 标记 pass/warning/block → 定向修复 → 重建验证。

**② 索引健康度（知识入库后）**

每个 `(资产, 知识类型)` 组合独立追踪：PENDING（待索引）→ INDEXED（已就绪）→ STALE（过期，需要重建）。大纲变更、chunk 变更自动触发 STALE。

**③ 检索效果（面向最终用户）**

构建 golden query 评估集（目标 70+ 条，覆盖 7 种检索模式），每次检索链路变更后自动回归：

| 指标 | 含义 | 目标 |
|------|------|------|
| Top-5 召回率 | 正确答案在前 5 个结果中的比例 | ≥ 80% |
| 答案上下文覆盖率 | 返回的上下文是否完整覆盖了答案所需信息 | ≥ 80% |
| 引用精确率 | 回答引用的具体段落能否在原文中定位到 | ≥ 95% |
| 章节命中率 | 政策/报告类问题的章节定位准确度 | ≥ 70% |
| 弱证据占比 | 返回的无关内容比例 | 越低越好 |

**评估集设计**（持续建设中）：
- 15 条政策/报告章节级 golden case（跨 5 份 PDF，覆盖"预期章节命中 ≥ 70%、不跨报告混入"场景）
- 7 类检索模式 × 2 条基线 × 5+ 领域 = 目标 70 条

## 第 13 页 — 总结

**核心交付**：

建成了一套**从数据加工源头到检索最终回答的完整质量保障体系**，覆盖 9 类异构资产的全链路。

**三个关键设计理念**：

1. **加工质量决定检索天花板**——10 道切块工序不是过度设计，而是每一道都在解决实际文档中会出现的真实问题。切块质量报告让"切得好不好"从主观判断变成可量化、可追踪的指标。

2. **不依赖完美数据**——标准编码在现实数据源中可得率极低，方案从设计上就不依赖它。L1+L1.5+L4 自给自足，字典和编码是增量，有就更好，没有也不垮。

3. **可观测、可回退**——每一层优化都有独立的开关、独立的评估指标、独立的回退路径。查不到结构化结果 → 自动回退全文向量搜索。LLM 分派失败 → 7 种 fallback 路径兜底。
