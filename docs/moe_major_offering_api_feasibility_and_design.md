# 教育部专业布点 API 同步可行性与设计建议

日期：2026-10-23。状态：已完成只读接入验证并实施已确认方案；代码、版本迁移及验证结果见 `docs/review/wk_moe_major_offering_implementation_evidence.md`。

用户边界：专业布点改为教育部政务服务平台 API 同步，先验证可行性；同步结果直接写入领域数据库，不存在 AI 治理；原专业布点 Pipeline 废弃。按“同一年份、相同学校、相同专业”判定同一份业务数据，重复跳过；不保存用于追溯的来源页号和内容哈希。新控制台列表只读，不提供编辑、删除；旧 Pipeline 退役必须同步清理 AI 治理规则、配置与数据库生效配置版本。

## 1. 结论

**技术上可行，适合接入现有 API 数据同步控制面，采用后端低频分页拉取、确定性校验、直接领域入库。**

- 用户给出的接口就是官方结果页实际调用的接口，返回原生 JSON；本次普通 HTTPS GET 未提供登录、Token、Cookie、Referer 或浏览器环境，也成功返回数据。
- 所需七个业务字段全部存在；年份来自请求上下文，不能把“年限”当成“年份”。
- 北京单页、江苏两页、山东和广东各三页已验证记录总数和跨页无重复；部分请求首次业务报错，有限重试后取得完整结果。
- 接口存在 HTTP 200 内嵌业务错误、实际 pageSize 与请求不一致、超范围页重复返回等行为，必须在适配器内处理。
- 本次是指定地区、年份、专业的采样验证，不是全国全专业或长期可用性验证。公开网页调用接口不等于提供了正式开放 API 的版本、限额和服务等级承诺。

## 2. 官方页面与接口事实

| 用途 | 地址或行为 | 实测结果 |
| --- | --- | --- |
| 查询页 | `https://zwfw.moe.gov.cn/zyyxzy/index.html` | HTTP 200，源码使用年份、省份字典 |
| 结果页 | `https://zwfw.moe.gov.cn/zyyxzy/result.html` | HTTP 200，源码直接 GET major-register 并展示七列 |
| 数据接口 | `https://zwfw.moe.gov.cn/eduSearch/api/major-register` | 参数 `year`、`province`、`majorCode`、`majorName`、`page`、`pageSize` |
| 年份字典 | `https://zwfw.moe.gov.cn/eduSearch/api/years` | 成功返回 2026 至 2013；第一次超时，重试成功 |
| 省份字典 | `https://zwfw.moe.gov.cn/eduSearch/api/provinces` | 成功返回 32 项，包含新疆生产建设兵团 |

页面标题是“高等职业教育专科拟招生专业设置备案结果”。因此接入对象应明确为**高职专科拟招生专业设置备案明细**，不能泛化成覆盖本科、研究生、全部在校专业或招生人数的数据源。

省份参数采用上游字典，存在 `HeB`、`HeN`、`HuB`、`HuN`、`SXS`、`XJBT` 等值，不能统一转大写或自行根据省份拼音生成。界面使用“省份/地区”标签可容纳兵团；保留上游编码和显示名称，若需行政区划码另做显式映射。

`robots.txt` 实际返回平台 HTML，不能据此认定存在允许或禁止采集的 robots 规则。本轮没有查得正式 API 使用说明或服务等级承诺，也未做限流压力测试。

## 3. 返回结构与字段映射

成功响应示例，取自 2026 年北京电子商务查询：

```json
{
  "msg": "查询成功",
  "data": {
    "total": "19",
    "list": [
      {
        "prov_name": "北京市",
        "major_code": "530701",
        "major_name": "电子商务",
        "school_code": "4111010037",
        "school_name": "北京物资学院",
        "school_system": "2",
        "remark": null
      }
    ],
    "currentPage": 1,
    "pageSize": 50
  },
  "success": true
}
```

上例仅截取一条明细，原响应含 19 条。

| 业务字段 | 上游字段 | 建议领域字段 | 规则 |
| --- | --- | --- | --- |
| 年份 | 请求 `year` | `year` | 必填整数，来自运行冻结参数；响应明细不含年份 |
| 省份/地区 | `prov_name`、请求 `province` | `province_name`、`province_code` | 必填，核对返回名称与请求字典项一致 |
| 专业代码 | `major_code` | `major_code` | 必填字符串，保留前导零 |
| 专业名称 | `major_name` | `major_name` | 必填，保存返回原值，校验专业代码对应请求 |
| 学校标识码 | `school_code` | `school_code` | 可空字符串，不作为唯一必备主键 |
| 学校名称 | `school_name` | `school_name` | 必填 |
| 年限 | `school_system` | `study_duration` | 必填文本，本轮有 `2`、`3`、`5`，不预设仅三年制 |
| 备注 | `remark` | `remark` | 可空文本 |

可以额外保存可解析的数值年限作为派生值，但原文本必须保留，不把特殊年限强制转换成错误整数。七个字段之外的学历层次可按该服务固定范围标为高职专科，并注明来源是服务范围。

## 4. 实测请求与异常

各专业查询使用专业代码 `530701`、专业名称“电子商务”，除表中变化项外使用 2026 年。

| 验证项 | 实测结果 | 工程含义 |
| --- | --- | --- |
| 北京第一页 | total=19，19 条，14 个不同学校标识码 | 按用户业务唯一性，首次同步新增 14 条、跳过 5 条 |
| pageSize=100 与 pageSize=1 | 都返回 pageSize=50，北京均为 19 条 | 用响应 pageSize 计算页数，本轮观察到请求值未生效 |
| 北京第二页（越界） | currentPage=2，但仍返回与第一页相同的 19 条 | 不能依靠空页作为唯一终止条件 |
| 江苏两页 | total=70，50+20，70 个不同明细键，68 所学校 | 正常多页可完整读取 |
| 山东三页 | total=120，50+50+20，120 个不同明细键，85 所学校 | 末页首次 HTTP 200 / 业务 500；重试成功 |
| 广东 2026 三页 | 第 1、2 页及学校名缩小查询曾返回业务 500；随后取得 50+50+30，共 130 个不同明细键、71 所学校 | 无法把一次业务错误当成空结果，也不能据此断言该省永久不可用 |
| 广东 2025 第一页 | total=131，返回 50 条 | 年份与地区组合需要独立判断 |
| 北京 2025 对比 2026 | 都为 19 条，但无序集合各有 2 条不同 | 年份筛选有效，不能只根据条数判断是否生效 |
| year=2099 | success=true，total=0，空数组 | 创建计划应校验上游有效年份 |
| 专业名称或代码互相不匹配 | success=true，total=0 | 两个查询条件同时参与筛选；零条不等于数据源异常 |

各原始请求的摘要以配套 JSON 证据为准，共记录 20 次数据接口请求及年份、省份字典结果。此前跨页验证使用的来源明细键包含年限，只用于核实源接口分页事实。实际入库按用户确认的年份、学校、专业去重，年限不参与业务唯一性。

错误正文实际示例：

```json
{"msg":"未知错误！","code":500}
```

即使 HTTP 为 200，也必须判定该页失败。`total` 是数字字符串，需受控转换；`success=true`、`data` 结构、`list`、`currentPage`、`pageSize`、`total` 均需校验。

## 5. 业务唯一性与重复跳过

**同一年份、同一学校、同一专业只保留一条业务记录。** 去重跨分页、同步计划、同步运行生效，不因来源、年限、备注或不同查询参数而重复入库。专业使用 `major_code` 识别，专业名称作为业务属性。

- 学校有标识码时优先按标识码匹配；缺码时按保守规范化学校名匹配；只有一方有学校码时，同时检查同年、同专业下的同名记录，避免缺码与有码形成两条。
- 学校名规范化仅做 Unicode 规范化、去除首尾空白等确定性处理，不模糊匹配、简称扩展或 AI 合并。学校名称必填，身份冲突显式记录错误。
- 年限不同、备注不同仍属于重复项。采用“首次成功入库保留，后续重复跳过”，不覆盖已有年限、备注等业务字段，不合并生成新年限值。
- 未命中唯一性才新增，命中即增加 `skipped_count`；重复不计为失败，也不影响同步成功判定。
- 同一专业跨省聚合统计的是已同步覆盖范围内的学校数；跨多个专业时，专业布点记录数与不同学校数分别统计。

实测样本在空业务表首次同步时的预期：

| 地区 | 接收原始条数 | 新增业务记录 | 重复跳过 |
| --- | --- | --- | --- |
| 北京 | 19 | 14 | 5 |
| 江苏 | 70 | 68 | 2 |
| 山东 | 120 | 85 | 35 |
| 广东 | 130 | 71 | 59 |
| 合计 | 339 | 238 | 101 |

再次完整同步相同数据，预期新增 0 条、跳过 339 条。来源中未再出现的已有记录不自动删除；同步是新增补充和重复跳过，不是全量替换。

## 6. 建议接入流程

```text
API 数据同步：教育部政务服务平台 Provider
  → 创建计划（年份、省份、专业名称、专业代码、频率）
  → data_sync_run 冻结查询参数
  → 后端 HTTPS GET 分页拉取
  → 确定性字段校验、参数一致性校验、幂等去重
  → 直接写专业布点领域表，并保存来源与运行关联
  → 记录新增/跳过/失败数量，更新同步运行结果
```

没有 AI 分类、Prompt、AI 评分、人工治理队列或语义索引步骤；不生成 `governance_result`，也不为满足旧表外键而伪造 `normalized_asset_ref`。这是独立 API 同步领域，不适用旧 Asset Pipeline 的阶段和资产版本状态要求。

确定性校验仅保证数据结构、来源与同步完整性，不推断、改写或补造教育部业务事实。学校代码可空、备注可空不作为失败条件；必填字段缺失、跨省/跨专业返回、类型错误必须留下错误与来源。

## 7. 与现有同步框架的真实差异

已核对当前代码，而不是直接沿用较早的实施计划文档：

- 可复用 `data_sync_config`、`data_sync_run`、调度、Worker 租约、查询快照、运行记录、审计和 `/data-sync` 控制台。
- 当前实现允许无未终态运行时编辑计划名称、频率和业务参数，Provider 固定。旧实施计划中“计划不可编辑”的描述已落后于当前 `SPEC.md` 与代码。
- 框架新增明确的 `auth_mode=none|tenant_token`，作为通用 Provider 能力。教育部及类似无需认证的国家机构开放 API 使用 none；该模式不要求 tenant_id/name/key，不获取、缓存或刷新 Token，不发送 Authorization；控制台显示“无需认证”。tenant_token 模式继续校验租户凭证并保留岗位现有行为；旧配置缺省按 tenant_token 解释。认证模式由部署配置固定，鉴权失败不能自动降级为 none。
- 岗位 Provider 是外部 submit/status/fetch 任务；教育部是直接分页 GET，没有已验证的外部任务或控制 API。建议增加 `execution_mode=paged_pull|external_job`，paged_pull 在本地运行与分页边界处理暂停、恢复、取消；不要声称教育部存在任务提交、轮询或控制端点。
- 现有 result handler 是明确的领域入库扩展点，可以复用短事务的“本页落库与游标同时提交”原则；HTTP 请求始终在数据库事务外。
- Provider 固定 base URL 为 `https://zwfw.moe.gov.cn`，适配器固定接口路径；用户表单不接受任意 URL、请求头或 Cookie。

## 8. 领域存储建议

新建独立的 `major_offering_record`，每条记录表示一个年份、一所学校、一个专业的布点数据。直接关联首次入库的同步运行，独立于资产版本、标准化引用和治理表。

建议字段：

```text
id
sync_run_id                 FK → data_sync_run，首次入库来源
provider_code
year
province_code / province_name
major_code / major_name
school_code                 nullable
school_name
study_duration
remark                      nullable
school_name_key             保守规范化学校名，用于无标识码时判重
source_url                  固定来源查询页 URL
fetched_at / created_at / updated_at
```

不保存来源页号、内容哈希、去重键哈希或逐条来源 JSON。追溯使用来源 URL、首次入库运行与采集时间；完整查询参数保存在既有 `data_sync_run.query_snapshot`。框架原有 query_hash 是查询参数幂等机制，不是新增的业务内容哈希。

数据库至少设置以下唯一约束，作为并发与重试的最终防线：

```sql
UNIQUE (year, school_name_key, major_code)
CREATE UNIQUE INDEX uq_major_offering_school_code
  ON major_offering_record (year, school_code, major_code)
  WHERE school_code IS NOT NULL;
```

空学校码统一转为 NULL。唯一键不包含同步运行、计划、Provider、省份、专业名称或年限。插入采用 `ON CONFLICT DO NOTHING RETURNING id` 区分新增与跳过；应用先检查学校身份冲突，不能把两个不同学校码但相同名称的冲突静默合并。

**采用全局业务去重与新增补充，不按运行重建业务快照。** 已存在记录直接跳过，不因同步成功、失败或零结果而覆盖、清空已有数据。每页新增记录即时提交并可查询；后续页失败保留已新增记录，页面明确显示该范围本次尚未同步完整，恢复时从运行游标继续。

重复项不覆盖首次入库值，首次成功保留的年限取决于首次收到的有效记录；上游排序稳定性没有承诺，不能将其描述为全部学制或“优先年限”。重复项不更新业务表采集时间；本次再同步的过程通过运行统计追踪。

## 9. 完整性、重试与调度

1. 从字典校验年份和省份，冻结四项查询参数；专业代码和名称一并编码发送，不静默丢弃名称。
2. 第一页读取 total 与实际 pageSize，计算 `ceil(total / pageSize)`；total=0 时本次无需继续拉页。
3. 严格限制页号不超过计算页数，避免已观测的越界重复页。
4. 每页检查业务成功、返回页号、范围一致性，短事务完成业务记录插入、运行游标和计数更新；不持久化来源页号或内容哈希。运行游标只用于恢复下一页。
5. 检查各页 total 一致、累计接收数与 total 一致；业务重复正常跳过。无无效记录时满足 `processed_count = success_count + skipped_count`，其中 success_count 是本次新增数，不能要求它等于上游 total。当前采用页号、页大小、total 与累计条数联合校验，不根据业务重复数量判断分页失败；不拒绝正常跨学制重复。
6. HTTP 超时、429、5xx 和本次观测到的业务 code=500 做有限退避重试；当前复用框架最多 3 次执行，退避 5/10 秒，遇 Retry-After 延后至其要求时间（上限一天）。未知 HTML 或结构漂移明确失败。
7. 重试耗尽保留本次已新增记录、运行游标、请求上下文和错误；显示“本次未完成”。恢复或重跑时对已存在数据跳过，已有数据不回滚删除。单页重试仅在落库和游标事务未成功时重放，不重复累加已提交页的计数。
8. 来源没有已验证的 snapshot token 或更新时间水位。跨页总数和页号检查只能发现部分变化，不能证明源端事务快照一致性；不据此承诺严格时点一致。

P0 建议一次运行仅一个年份、省份、专业组合，省份和年份使用字典下拉。沿用当前五档频率，默认一年，可月度补采和手动执行；年份是固定条件，不随新年自动滚动。单 Provider 先限制一个在途请求，页间至少一秒；这是本地保守配置，未经压测，不能称为上游官方限额。

## 10. 控制台与查询建议

- `/data-sync` 增加“教育部政务服务平台”卡片，描述“高职专科拟招生专业设置备案结果”，关联官方查询页。
- 创建计划必填：年份、省份、专业名称、专业代码；同时保留通用计划名称和频率。分页参数由适配器管理。
- 计划编辑、复制、暂停、恢复、删除、手动运行沿用现有语义。暂停计划与暂停当前运行明确区分；运行控制只控制 NEXUS 拉取行为。
- `/asset-center/major/distributions` 读取新领域表，列为年份、省份、专业代码、专业名称、学校标识码、学校名称、年限、备注；展示同步范围、新增/重复跳过/失败数量、最近同步状态与时间。
- 新专业布点列表只读：移除单条和批量“编辑/删除”按钮、操作列及对应弹窗、表单、请求与前端状态。不提供人工覆盖层。新增业务模型只开放查询/聚合，入库仅由同步 Worker 执行；旧专业布点 PATCH/DELETE 接口随退役移除，直接调用也不能修改或删除数据。此限制针对业务记录，不影响同步计划自身的编辑、暂停或删除。
- 业务接口仍由 `nexus-api` 所有，建议新增 `/v1/major-offerings` 与 `/v1/major-offerings/aggregate`，沿用部署现有鉴权/公开 API 路由组织。支持四项核心条件、学校条件和分页，聚合分开返回明细数与学校数；返回 source、同步时间与覆盖范围。
- 原专业布点 Pipeline 正式退役：移除文件导入类型入口、自动识别和任务路由、领域 writer、该类型 AI 治理配置、知识处理触发及对应重处理入口。只退役专业布点分支，不删除其他类型共用 Pipeline 能力。存量未执行任务标记取消或明确退役失败，避免继续写旧领域表；不重写历史审计。
- 业务页面、查询接口、检索路由与发现描述统一切换新领域数据，不读取、聚合或回退到旧专业布点处理结果。旧流程不作为本方案前提，不建设双写或兼容分支；历史清理另行处理，不在退役时自动删除历史数据库记录或原始文件。
- 公开来源不取消 NEXUS 的调用权限与审计；来源默认为 L1 公共信息，无需构造 L3/L4 审批。

### 10.1 旧 Pipeline 的 AI 治理规则和配置退役

代码路径停止执行与配置数据退役必须在同次功能切换中交付。不能只改配置文件而遗留数据库当前生效规则，也不能仅停掉 Worker 分支却让管理台保存或重新 seed 时恢复旧能力。

已核实的清理对象：

| 对象 | 已有位置或行为 | 处理要求 |
| --- | --- | --- |
| 治理分类规则 | `config/governance_rules_v2.json` 中 `classifications.code=major_distribution` | 从当前治理配置移除该分类及其专属分类、质量、标签、准入和复核引用 |
| 知识处理配置 | 同文件 `structured_record_table.applicable_classifications` 当前仅含 major_distribution | 移除该适用项；当前专属配置无剩余使用方则移除整个配置，保留其他资产共用配置 |
| 治理种子与映射 | `nexus-app/nexus_app/ai_governance/seed_data.py` 中专业布点名称/代码映射 | 移除旧治理入口和种子映射，防止新装或 reseed 复活；新业务目录仍保留专业布点业务名称 |
| 结构质量与运行分派 | `governance/decision_service.py` 的专业布点结构检查、profile detector、record body adapter、domain writer 注册 | 删除或解除专属调用和注册，旧任务不能继续进入治理或领域写入 |
| 数据库当前配置 | `governance_rules_version`；部署中若存在专属 `ai_analysis_rules` / `ai_prompt_profile` | 版本迁移清理当前生效内容；专属分析规则和 Prompt 按各自生命周期禁用/归档，不删除共享治理 Prompt |
| 业务读写接口 | 内部旧专业布点记录 PATCH/DELETE 及控制台调用 | 移除旧修改入口，新业务记录无人工编辑/删除接口 |

清理依据稳定代码、领域配置键和实际引用关系，不根据中文“专业布点”全文匹配批量删除。检索意图、业务目录、专业布点查询工具仍是新领域的有效能力，只切换其数据来源，不把它们当成旧 AI 治理规则一起删掉。

### 10.2 数据库配置版本迁移

新增 Alembic 数据迁移，沿用项目已有的“归档旧生效规则、创建清理后新生效版本”机制（可参考 `20261012_0115_retire_job_demand_pipeline_b.py`），不修改已执行的历史迁移文件。

1. 读取并锁定当前生效的 `governance_rules_version`，在其内容上定向清理专业布点相关配置，保留部署已有的其他业务规则和人工定制内容；不能用仓库默认 JSON 整体覆盖数据库。
2. 旧版本仅变更为 archived，`rules_content` 保持原值；新增版本号基于数据库现有最大版本递增，新版本保存清理后的内容、变更说明、操作身份与 trace_id，并设为 active。仍维持现有单一生效版本约束；遇到多个生效版本应显式报错，不猜测覆盖。
3. 在同一迁移事务中禁用/归档已确认的专业布点专属分析规则与 Prompt。若配置表采用内容不可变版本，创建停用后继版本；保留历史运行引用、历史规则内容与历史审计，不直接删除被引用的配置行。
4. 若当前配置已清理，迁移不重复生成相同内容版本；没有生效版本时不凭空重置系统规则。运行时配置缓存应失效或在部署后重载，确保新运行不使用旧缓存。
5. 同步更新仓库默认规则、seed 和配置引用校验，保证“全新安装”和“存量数据库升级”得到一致的有效配置。配置内容变化使用规则数据版本递增，结构未变化时不随意修改 schema_version。
6. 迁移记录本次前后版本 ID、专属配置停用数量及变更原因；发布证据包含 Alembic revision 和当前生效配置检查。回滚不能单独重新激活旧规则，需与旧执行代码配套评估，避免配置指向已移除的 Pipeline。

验收必须覆盖：新装无旧治理分类；存量升级产生清理后的新版本且旧规则内容不变；非专业布点定制规则不变；重复执行清理逻辑不生成额外版本；共享 Prompt 不受影响；重新 seed 不恢复已退役配置；直接调用旧 PATCH/DELETE 不产生写入；新列表不存在编辑/删除能力。
