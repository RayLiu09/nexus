# 人才需求调研分析报告 — 执行参考

单专业《人才需求调研分析报告》执行规则：保存待确认大纲 → 等待确认 → 轻量口径初始化 → 建报告骨架 → 按章节证据包逐 section 写入正文。

报告的核心目标是贯彻落实职业教育教学关键要素改革要求，围绕产业环节、生产流程、业务流程和职业逻辑，联通“产业—行业—职业—专业”链条，实现人才培养供给侧与产业需求侧在结构、质量上的匹配，助力学校专业建设和专业群建设。

报告必须回答以下核心问题（不得写成单纯行业介绍、政策摘录或岗位统计清单）：

1. 本专业服务什么产业、产业链哪些环节、哪些业务领域。
2. 产业数字化转型、“四新”变化对岗位能力提出了哪些新要求。
3. 专业面向哪些岗位群、岗位层级和核心岗位。
4. 核心岗位承担哪些典型工作任务。
5. 完成这些工作任务需要哪些知识、技能、素养和工具。
6. 现有人才培养供给与产业需求之间存在什么结构和质量差距。
7. 课程、实践、教材、师资和校企合作应如何更新。

---

## 一、执行流程

1. 确认会话已绑定项目，且项目输入含 `industry`、`province`、`city`、`specialtyName`、`educationLevel`。
2. 按第二节固定六章生成大纲，调用 `save_artifact` 保存为 `demand_outline`。
3. 等用户确认或编辑大纲。
4. 大纲确认后先读回最新 `demand_report`。仅首次生成或用户明确要求重新生成整份报告时调用 `start_artifact_generation` 创建新版本并建骨架；最新报告仍为 `generating` 且已有骨架时，复用原 `recordId` 从首个未完成 section 继续，禁止再次 start 或重建骨架。
5. 报告采用「随需检索、逐章推进」，不一次性前置把全报告数据查完：开头只做一次轻量口径初始化（专业、区域、产业面向、岗位边界等项目级公共口径），其余按需检索、逐章积累证据。
6. 检索由数据需求驱动、不按固定节奏：凡要写可验证的外部事实（见 §三·4「必须加角标的事实」）前，必须已有对应的真实检索来源，没有就先检索；纯综合判断、基于已掌握证据的推理、优化建议与框架性说明不额外检索。产业发展与环境分析、行业人才需求分析、人才供需匹配分析三章数据密集，每章至少检索一次，不得整章仅凭常识铺陈。检索后形成本节内部证据包：分析目标、可用证据、缺失与降级、表格 / 图表 / 图谱任务、可写结论与禁止写结论。
7. 每个 section 写入前完成格式 / 证据 / 可视化 / 术语自检；每进入新 section 先输出一句业务语言的进度提示——需要检索时先报一句「正在检索…」、检索完或无需检索时报「正在撰写…」——再通过 `begin_artifact_draft` / `write_artifact_draft` / `commit_artifact_draft` 写入正文。
8. 骨架中的每个 section 都必须写入正文并提交：一级章 section 写 1-2 段开篇综述，二级节 section 写该节完整正文；不得只生成二级节而让一级章保持空正文。
9. 全部 section 提交后，调用 `end_artifact_generation({ artifactType:'demand_report', recordId:'<reportRecordId>', status:'completed' })` 结束本次报告生成。

### save_artifact 契约

> 所有 `save_artifact` 调用，参数顺序一律 `artifactType` → `recordId`（如有）→ `payload`。payload 往往很大，必须放最后：放前面会让右侧面板一直等到整包 payload 传完才一次性渲染。

**保存大纲：**

`demand_outline` 只保存一级章和二级节。`sections` 必须是按最终出现顺序排列的一维数组；`level=1` 表示章，`level=2` 表示节。每个章后必须紧跟至少一个属于该章的节。

```text
save_artifact({
  artifactType: 'demand_outline',
  payload: {
    title: '<专业名>人才需求调研分析报告',
    sections: [
      { level: 1, title: '<第一章标题>' },
      { level: 2, title: '<第一章第一节标题>' },
      { level: 2, title: '<第一章第二节标题>' },
      { level: 1, title: '<第二章标题>' },
      { level: 2, title: '<第二章第一节标题>' }
    ]
  }
})
```

上例只展示拍平方式；实际保存必须按第二节生成完整六章及其全部二级节。禁止把节嵌套在章对象中，例如 `[{ title:'报告说明', subSections:[...] }]`；也禁止在大纲 payload 中写 `thirdLevels`。三级标题不是大纲面板数据，生成对应二级节正文时再按本文件的标题规则写入正文。

**开启报告新版本：**

```text
start_artifact_generation({
  artifactType: 'demand_report',
  title: '<专业名>人才需求调研分析报告'
})
```

记录返回的 `recordId` 为 `reportRecordId`。

**建骨架：**

```text
save_artifact({
  artifactType: 'demand_report',
  recordId: '<reportRecordId>',
  payload: {
    sourceRecordId: '<已确认大纲 recordId>',
    title: '<专业名>人才需求调研分析报告',
    sections: '<复用已确认大纲 sections，仅保存 { seq, level, title }，不写正文>'
  }
})
```

**正文草稿写入：**

```text
begin_artifact_draft({
  artifactType: 'demand_report',
  recordId: '<reportRecordId>',
  target: {
    kind: 'section',
    seq: <本节 0 基序号>,
    title: '<本节标题>'
  }
})
```

`begin_artifact_draft` 必须独占一轮，等待 `{ draftId }` 后才能：

```text
write_artifact_draft({
  draftId: '<begin 返回的 draftId>',
  content: '<本 section 正文，不含标题编号>'
})
```

写入后提交：

```text
commit_artifact_draft({
  draftId: '<begin 返回的 draftId>'
})
```

正文提交必须覆盖大纲中的全部 section。一级章不是纯目录节点，也要按自己的 seq 独立执行 `begin_artifact_draft` / `write_artifact_draft` / `commit_artifact_draft`。

### 逐章进度提示（强制）

报告要写几十次草稿，若中途一直静默连续调用工具，用户无法感知进度。因此**每个 section 开写前必须先输出一句进度提示**，把冗长的写作过程切成用户可感知的节奏：

- **时机**：每次 `begin_artifact_draft` 之前，先单独输出一句面向用户的进度文本，再开始该 section 的草稿三件套。
- **内容**：只说“正在写哪一章/节”，进入新一级章时可顺带报告上一章已完成并自然过渡。示例：
  - 进入一级章：`第二章已完成。进入核心章节：三、行业人才需求分析。`
  - 写二级节：`正在撰写：3.2 岗位能力要求分析。`
- **措辞约束**：只使用业务章节名与阶段名；**禁止**出现工具名（begin/write/commit_artifact_draft 等）、seq、recordId、draftId、字段名、表名。
- **粒度与长度**：一句话即可，不展开正文内容、不逐条罗列；一级章过渡必给，二级节至少在进入每节时给一句。
- **目的**：让用户始终知道“写到第几章、下一步做什么”，而不是看到一长串无说明的工具调用。

全部 section 提交完成后，必须显式调用：

```text
end_artifact_generation({
  artifactType: 'demand_report',
  recordId: '<reportRecordId>',
  status: 'completed'
})
```

## 二、大纲结构规则（一级章固定，二级节按需）

- **一级章固定**：必须是下列 6 个一级章，名称、顺序、数量都不得改动或增删。
- **二级节按需**：下列每章的二级节只是**参考清单**，模型应结合具体专业与调研实际，自行增删、改写、合并——不必逐字照搬、也不必凑够列出的条数；但每个一级章下都要有能支撑本章分析的二级节，不能出现空章。

```text
一、报告说明
  （一）报告背景与目的
  （二）研究对象与范围
  （三）数据来源与方法
二、产业发展与环境分析
  （一）产业政策环境分析
  （二）产业发展现状
  （三）区域产业链与业务领域分析
  （四）重点企业与典型应用分析
  （五）产业发展趋势与四新变化
三、行业人才需求分析
  （一）产业链环节与人才需求总体特征
  （二）岗位群需求结构与岗位层级校准
  （三）岗位图谱分析
  （四）新技术新工艺与岗位能力变化分析
  （五）新兴岗位趋势与培养调整指向
四、专业人才培养现状分析
  （一）专业布点与招生计划分析
  （二）课程体系分析
  （三）人才培养质量分析
  （四）校企合作与实践体系分析
五、人才供需匹配分析
  （一）供需规模匹配
  （二）结构匹配分析
  （三）主要供需矛盾分析
  （四）问题成因分析
六、专业人才培养优化建议
  （一）人才培养定位优化
  （二）人才培养目标优化
  （三）课程体系优化建议
  （四）实践教学体系优化建议
  （五）校企合作机制建议
  （六）师资队伍建设建议
```

### 标题硬规则

以下三级标题规则只用于后续 `demand_report` 正文，不属于 `demand_outline.sections` 的数据结构。

- 所有二级标题下必须设置三级标题。
- 每个二级节至少 2 个三级标题。
- 重点分析类二级节应包含 3—5 个三级标题。
- 三级标题格式只能为：

```text
**1. 标题**

正文……

**2. 标题**

正文……
```

- 禁止使用 `1. 标题`、`1、标题`、`1）标题`、`（1）标题`、`① 标题`、`#### 1. 标题`。
- 禁止四级标题。
- 禁止二级节直接输出连续段落。

### 全文禁用章节指代

正文全文禁止出现：

```text
本章、上一章、下一章、前几章、前三章、前五章、第二章、第三章、第四章、第五章、第六章、结合第几章、为第几章提供依据
```

替代表达：

| 禁用表达 | 推荐表达 |
| --- | --- |
| 本章分析 | 该部分围绕……展开分析 |
| 结合第三章和第四章 | 基于岗位需求与培养供给两类证据 |
| 为第六章提供依据 | 为后续培养优化提供问题依据 |
| 前三章分析表明 | 前述产业、岗位与供给分析表明 |

### 正文表达规则

- 不得大量使用“关键发现：”“核心判断：”“培养启示：”“成熟度：”等“词+短句”标签。
- 可以加粗关键判断，但必须嵌入连贯段落。
- 推荐写法：`岗位需求正在从基础操作型向数字化运营型升级，这意味着课程内容不能停留在平台操作层面，而应进一步强化数据分析、智能工具应用和业务决策训练。`
- 禁止写法：`核心判断：岗位需求正在升级。培养启示：课程要调整。`

## 三、政策、标准与数据源规则

### 1. 政策时间窗

政策分析必须优先检索：

1. 2026 年政策、年度工作要点、政府工作报告、行动方案、实施方案、专项政策；
2. 2025 年政策；
3. 2024 年政策。

原则上不使用 2023 年以前政策作为当前依据。正文不得出现“十四五”。如确需引用较早文件，只能作为前期政策基础或历史背景，不得作为当前政策依据。

政策检索关键词必须包含：

```text
地区 + 产业关键词 + 2026 + 政策 / 行动方案 / 实施方案 / 工作要点 / 政府工作报告 / 人才政策 / 产教融合 / 职业教育 / 新质生产力
```

### 2. 专业教学标准边界

专业教学标准、职业分类、职业标准、证书标准属于标准依据，不属于政策文件。

禁止：

- 将专业教学标准写入政策汇总表；
- 将专业教学标准称为国家政策文件；
- 在产业政策环境分析中把专业教学标准当作政策依据展开。

正确用法：

- 用于岗位基线；
- 用于能力要求；
- 用于课程参照；
- 用于证书对照；
- 用于校准岗位名称和岗位层级。

### 3. 新质人才与紧缺人才目录

岗位分析必须检索国家、省、市三级新质人才、急需紧缺人才、紧缺职业目录。优先检索 2026 年，其次 2025 年和 2024 年。

必须输出“新质人才与紧缺人才目录对照表”：

| 目录名称 | 发布单位 | 发布年份 | 涉及职业/岗位 | 与本专业关联 | 对岗位分析的启示 |
| --- | --- | --- | --- | --- | --- |

若未检索到对应目录，应在数据局限中说明“公开资料未检索到当前年度相关目录”，不得编造。

### 4. 引用与来源标注

- **角标格式**：正文关键数据与判断处加角标，`[[N]](#ref-N "标题；发布机构；发布时间；链接或知识库文件")`——`N` 是编号，`title` 内放来源摘要（供悬浮查看）。
- **全局连续编号**：编号全报告统一，按正文首次出现顺序连续编号；同一来源在后续章节、图表复用同一 `N`；不同统计口径即使同源也拆成不同编号。
- **只引真实来源**：只标真实检索到的来源，禁止为凑角标编造来源或链接；检索不到就不写该具体值，并在数据局限中说明。
- **必须加角标的事实**：政策条款与年份、产业规模 / 增长率 / 企业数、岗位与样本数量、薪资 · 学历 · 经验比例、院校布点 · 招生 · 就业等目标院校事实、专业教学标准与职业标准要求、任何具体统计数字；纯判断与建议不加。
- **图表来源**：图表代码块后写可见的「数据来源：短名；口径」，不在图上放角标；图表解释文字含判断时仍加角标。
- **文末参考文献**：全报告在最后一章（专业人才培养优化建议）末尾统一生成一次《参考文献》，每条一行、之间留空行，格式 `[N] 标题. 发布机构. 发布时间. 获取日期：YYYY-MM-DD. 链接：<如有>.`；编号与正文角标一致，禁止只写 `[N]` 而无内容。

## 四、章节写作规则

### 一、报告说明

必须包含三级标题：

**1. 报告生成背景**

围绕职业教育教学关键要素改革、产业链人才需求变化、学校专业建设需要说明报告背景。

**2. 报告分析目标**

说明报告不是行业介绍，而是为专业定位、课程更新、实践教学、教材更新、师资建设和校企合作提供依据。

**3. 报告分析逻辑**

说明“产业—行业—职业—专业”链条和“产业链环节—岗位群—任务—能力—课程/实训”链条。

数据来源与方法必须包含：

**1. 数据来源构成**

说明政策、产业、岗位、标准、院校、用户上传材料等来源。

**2. 数据使用方式**

说明各类数据用于哪些分析任务。

**3. 数据局限与待补充材料**

说明未获得的数据，不编造。

### 二、产业发展与环境分析

#### （一）产业政策环境分析

必须包含三级标题：

**1. 国家及行业政策环境**

重点检索 2026 年和近三年政策。

**2. 省级政策环境**

重点分析省级产业、人才、职业教育、产教融合、新质生产力相关政策。

**3. 市域政策环境**

重点分析城市产业布局、人才政策、园区政策、重点项目政策。

**4. 政策环境对人才培养的综合影响**

形成综合判断。

最后统一输出政策汇总表：

| 政策层级 | 政策名称 | 发布年份 | 发布单位 | 对人才培养的核心要求 | 对本专业建设的启示 |
| --- | --- | --- | --- | --- | --- |

专业教学标准不得出现在该表。

#### （三）区域产业链与业务领域分析

必须围绕专业服务的产业、产业链环节和业务领域展开。

必须输出“产业链环节—业务领域—岗位群关系表”：

| 产业链环节 | 业务领域 | 典型生产/业务流程 | 相关岗位群 | 本专业服务关系 |
| --- | --- | --- | --- | --- |

### 三、行业人才需求分析

该部分是报告核心，不得写成岗位统计。必须围绕专业所培养人才服务的产业链环节、业务领域、岗位群、岗位层级、任务和能力展开。

#### （一）产业链环节与人才需求总体特征

必须包含三级标题：

**1. 专业服务的产业链环节**

分析专业面向的产业链上游、中游、下游或业务链环节。

**2. 产业链环节对应的业务领域**

明确专业服务哪些业务领域，如运营、营销、服务、设计、数据、供应链、跨境等。

**3. 人才需求总体特征**

说明人才需求总量、结构、层级和变化趋势。

必须输出：

| 产业链环节 | 业务领域 | 核心岗位群 | 岗位层级 | 人才需求特征 |
| --- | --- | --- | --- | --- |

#### （二）岗位群需求结构与岗位层级校准

该部分只呈现归并后的结果，不展示底层算法、聚类过程、映射过程。

必须包含三级标题：

**1. 专业教学标准岗位基线**

## 五、图表与图谱规则

除少数汇总表（政策汇总表、主要岗位汇总表等）外，统计分布 / 趋势 / 关系 / 层级类数据统一用 ECharts 图表呈现，不用 Markdown/HTML 表格堆数值。图表数据必须来自真实查询或可核验公开来源，不编造。

### 1. 图表生成方式（必须用 `build_echarts_option`，禁止手搓 option）

正文不得手写 `tooltip / xAxis / series / encode` 等 ECharts 样板。统一走三步：

1. 准备**紧凑数据**（只有类目 + 数值，不含 ECharts 结构）。
2. 调 `build_echarts_option({ chartType, data, title?, sourceNote? })`，拿回完整 option JSON 字符串。
3. 把返回的 option **原样**贴进正文的 ` ```chart ` 代码块（语言标签必须是 `chart`，前端据此识别渲染）。

示例（岗位需求 TOP10 柱状图）：

```text
build_echarts_option({
  chartType: 'bar',
  title: '岗位需求TOP10',
  sourceNote: '来源：岗位招聘样本库；口径：<目标区域>、<产业/专业关键词>；样本量=<n>；统计时间=<范围>',
  data: { categories: ['<岗位A>', '<岗位B>'], series: [{ name: '需求量', values: [95, 82] }] }
})
```

### 2. 可用图表类型与适用场景

按数据形态选 `chartType`（**紧凑 `data` 的具体字段以 `build_echarts_option` 工具说明为准**，勿手写 option）：

| chartType | 适用场景 |
| --- | --- |
| `bar` | 岗位需求量 / 分类对比、学历或经验分布 |
| `line` | 年度趋势（需求、规模随时间），支持 smooth / area |
| `pie` | 占比（学历占比、岗位群占比、企业类型占比），可环形 |
| `radar` | 多维能力画像、典型岗位能力结构 |
| `scatter` | 双变量相关（如薪资 × 经验） |
| `gauge` | 单一指标达成率（谨慎使用） |
| `graph` | 岗位群—岗位—能力关系网络 |
| `knowledgeGraph` | 带关系标签的语义网络（岗位—任务—能力三元组） |
| `sankey` | 供需流向、产业链 → 岗位群 → 能力流转 |
| `tree` | 岗位群 / 能力层级结构 |
| `heatmap` | 能力覆盖、岗位群 × 能力强度；须解释横轴 / 纵轴 / 数值含义 |
| `wordCloud` | 岗位技能词频、能力关键词 |
| `custom` | 上述都无法表达的复杂图，透传完整 option |

统计分布优先 `bar/line/pie`；关系 / 层级 / 流向数据才用 `graph/knowledgeGraph/sankey/tree`。不滥用复杂图，同一份数据不用多个图重复展示。（工具不支持 treemap/sunburst 等类型，勿使用。）

### 3. 分章建议图表（图表要覆盖全报告，不只堆在第三章）

各章按数据是否充分选图；有量化数据才出统计图，有关系型数据才出关系 / 图谱图：

| 章节 | 建议图表 |
| --- | --- |
| 二、产业发展与环境分析 | 产业规模 / 结构趋势（`line`/`bar`）；产业链—业务领域关系（`graph`/`sankey`，有关系数据时）|
| 三、行业人才需求分析（核心，至少 3–4 张）| 岗位需求 TOP（`bar`）、学历分布（`bar`/`pie`）、经验分布（`bar`/`pie`）、薪资对比（`bar`，薪资数据有效时）；能力画像（`radar`）、岗位技能词频（`wordCloud`）；**岗位图谱（`graph`/`tree`，强制，见下方 §5）** |
| 四、专业人才培养现状分析 | 专业布点 / 招生计划变化（`bar`/`line`）|
| 五、人才供需匹配分析 | 供需规模 / 结构差距（`bar`）；能力覆盖强度（`heatmap`，有量化数据时）|
| 六、专业人才培养优化建议 | 一般以文字为主，不强制出图 |

样本不足或字段缺失时，说明限制并**减少图表**，不得补造；不为“显得丰富”而堆图。

### 4. 图文规范与真实性

- 每个图表前必须用 1–2 句说明“图表要回答什么问题”；图表后必须用一段解读“图表显示什么、说明什么供需问题、对专业定位 / 课程 / 实践 / 校企 / 师资有什么含义”，不得只复述数值。
- 图表正文附近必须有**可见**来源说明；`sourceNote` 用用户可读描述（不暴露表名 / 字段 / SQL），仍需保留供前端摘要。
- 能力雷达 / 能力热力 / 占比等**量化图必须来自真实统计**（技能标签统计、岗位描述词频、专家评分、院校课程覆盖）；纯模型归纳只能写成文字或普通条目，不得伪装成量化图。
- 岗位 TOP / 学历 / 经验 / 薪资等岗位图表必须标注样本量、统计时间、分类口径。

### 5. Graph 图谱强制规则

岗位工作任务与能力需求分析必须生成“岗位图谱分析”。

图谱必须包含：

- `graphName`
- `defaultView`
- `availableViews`
- `nodeTypes`
- `nodes`
- `edges`

`availableViews` 至少包含：

```json
["treeLeftToRight", "graph", "radialTree", "table"]
```

缺少上述字段，或 graphName 不是“岗位图谱分析”，质量检查不通过。

## 六、质量检查

### 1. 标题与格式质量门

- 任一二级节缺少三级标题，不通过。
- 三级标题未加粗，不通过。
- 三级标题不是 `**1. 标题**` 格式，不通过。
- 出现 `（1）`、`1）`、`1、`、`①` 作为标题或段落编号，不通过。
- 出现四级标题，不通过。

### 2. 政策与标准质量门

- 政策未优先检索 2026 年，不通过。
- 正文出现“十四五”，不通过。
- 政策汇总表出现专业教学标准，不通过。
- 专业教学标准被称为政策文件，不通过。

### 3. 术语质量门

- 出现“年制结构”，不通过。
- 招生规模、就业率、岗位数量、薪资、缺口规模等数值无来源却写具体数字，不通过（如就业率无来源却写“普遍超过95%”）。

### 4. 岗位分析质量门

- 未分析专业服务的产业链环节和业务领域，不通过。
- 未检索新质人才、急需紧缺人才、紧缺职业目录，不通过。
- 输出“岗位映射表”，不通过。
- 岗位名称未按培养层次校准，不通过。
- 中职主要岗位出现经理、总监、专家，不通过。
- 岗位图谱缺少 `graphName`、`defaultView`、`availableViews`、`nodeTypes`、`nodes` 或 `edges`，不通过。
- 图谱名称不是“岗位图谱分析”，不通过。
- 图谱主节点包含“课程/实训方向”，不通过。

### 5. 表达质量门

- 大量出现“关键发现：”“核心判断：”“培养启示：”“成熟度：”等标签式短句，不通过。
- 出现“本章”“前五章”“第六章”等章节指代，不通过。
- 建议部分出现“对应矛盾：”“调整对象：”“实施动作：”“预期改善点：”作为正文标签，不通过。

### 6. 图表质量门

- 第三章缺少核心分布图表（岗位需求 / 学历 / 经验；薪资数据有效时含薪资对比），不通过。
- 岗位图谱分析未生成 graph/tree 图谱，不通过。
- 正文手写 ECharts option（未走 `build_echarts_option` / 未用 ```chart 代码块），或使用工具不支持的 chartType（如 treemap/sunburst），不通过。
- 图表无图前说明、图后解读和数据来源，不通过。
- 写“下图”但没有 chart 代码块，不通过。
- 把模型主观归纳伪装成量化图（能力雷达 / 热力图等无真实统计来源），不通过。
